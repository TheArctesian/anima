## Approved foundation: operational key management

The VPS is the authoritative store for Anima's operational credentials, API keys and other runtime secrets. All servers admitted to the Anima network are trusted. They authenticate to retrieve the keys they need and may keep protected local caches. Do not introduce server trust tiers.

The intended behaviour is like Azure Key Vault: central encrypted storage, authenticated retrieval, versions and lifecycle metadata. This is a behaviour analogy, not a decision to use or provision Azure. The implementation/backend remains open.

### Foundation scope

- Extend/reuse the existing `credentials` domain for operational secret storage and encryption (SEC-003, SRC-008). Do not create a parallel credential store. Keep values out of repositories, logs, events, metrics and audit messages (LOG-007).
- Authenticate the requesting server against its admitted Anima identity before retrieval. Record which keys each server/workload consumes. Network presence alone is not authentication. This is server-to-server retrieval, not permission to send stored device passwords/private keys to operator clients (CLI-004, SEC-005).
- Protect local cached values at rest and in use with the platform's appropriate protected storage. A cache is a copy of a versioned VPS value, not another authoritative store. Cache handling must not expose values through diagnostics or error messages.
- Give each key version a stable identity and lifecycle state. Track creation, activation, supersession, expiry and revocation. Record the version used by each consumer so updates can be observed.
- After a version changes, notify or otherwise detect the change and refresh/invalidate affected caches. A connected consumer must stop using a revoked or superseded version according to the agreed lifecycle contract. Define acknowledgements, retry behaviour and recovery after reconnect; do not claim an unreachable cache was immediately erased.
- Removing a server from Anima must revoke its retrieval identity and prevent further fetches. Removing/revoking a key must prevent further retrieval and invalidate reachable caches. Define protected local removal on unenrolment. Previously fetched credentials cannot be recalled from an offline server; decide when provider-side revocation/rotation is required to stop their use.
- Keep metadata for key name, provider, purpose, consumers, current version, expiry, rotation interval/due state, instructions/provider link, last rotation time/operator and audit history. Metadata must not contain the secret value.
- Support manual provider rotation: store the instructions or provider link, accept the replacement value/version, and record completion and actor. Distinguish recording a rotation from actually rotating the provider credential. Do not imply arbitrary provider keys can be rotated automatically.

Operational consumers include source-account provisioning [KEYS](../extensions/KEYS.md) and compute provisioning/runtime infrastructure [KEYS-C](../compute/KEYS-C.md), [C1](../compute/C1.md). Keep their workflows separate; this issue owns the shared key-management foundation.

## Separate retained scope: personal-record sealing

Operational key distribution does not make personal vault master keys or Class A content server-readable.

Retain the original personal-record requirements and security-review obligation here until they are explicitly split into follow-up scope:

- **Class A:** the vault key remains in client OS key stores and is never sent to the hub or another server (VLT-001). Retain client-to-client enrolment and recovery (VLT-002), audited reveal without values (VLT-004), TOTP re-check (VLT-005), and sealed/client-side search (VLT-006). Personal Secrets [XP-04](../extensions/XP-04.md) and identity Documents [XP-09](../extensions/XP-09.md) retain their existing client-sealing protections. Their master keys are not operational secrets to distribute.
- **Health, money and location:** the operator permits these records to be shared/read across trusted Anima servers. Do not infer a device-only restriction for them. Keep personal-record encryption keys distinct from the operational credential encryption key (VLT-003); the detailed record-key/storage contract still needs alignment. Related placement issue [OD-E1](../decisions/OD-E1.md) is not rewritten by this clarification.
- Preserve ENG-011, PH-E-001 and PH-E-002: the security review must prove that the hub and server-side operational key retrieval cannot read a Class A value. The existing review gates for the affected personal-record workflows remain.

## Later screens

Expiry, rotation and key-management pages are later screen work. This foundation supplies their metadata and operations; it does not implement them. Existing Integrations UI context is [E0-2](E0-2.md); the personal Secrets workflow [XP-04](../extensions/XP-04.md) remains separate from operational key distribution.

## Acceptance and decisions still open

- Prove encrypted authoritative storage and protected caches, authenticated retrieval by admitted servers, rejection after server/key revocation, version refresh/invalidation and recovery after reconnect, and value-free audit/error output.
- Prove that operational retrieval cannot expose client vault master keys or Class A records. Complete the retained personal-record security review before declaring that scope done.
- Before implementation, settle backend selection, server authentication/enrolment, cache lifetime/offline behaviour and invalidation delivery, version activation/overlap rules, provider-side revocation responsibilities, and separation of operational versus personal-record key namespaces. No backend, arbitrary automatic rotation or hosted service is selected by this issue.
