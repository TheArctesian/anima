## Approved direction: reuse existing file access; add collection only when needed

Existing file access/sharing is sufficient for now. Use Anima's SSH/SFTP file access and transfer system as the backbone for future source imports. Do not build a mandatory separate `anima-collector` daemon, general cloud file-sync/storage layer or replacement transfer system as foundation work.

**Priority: later.** No new collection implementation is justified by this issue alone. A consuming feature must identify the selected source, required access, import behaviour and security boundary before an extension is built. Keep only the minimal hooks/import responsibilities that feature needs.

The [Phase 3 handoff](../../programme/handoff.md) records Phase 2 completed/merged, with O-4 SFTP live acceptance still pending at that checkpoint. Reuse the existing implementation; this clarification does not claim that pending live check has passed.

## Demand-driven import responsibilities

When a real consuming feature needs collection:

- Prefer scoped SSH/SFTP access to explicitly selected source files/folders. Do not broadly harvest a computer's files or traverse beyond the selected source. Preserve the selected-folder boundary and refusal to follow symlinks outside it (COL-006).
- Add parsing, incremental read positions and retry-safe import/checkpoint handling only for the source that needs them. Reuse the connection/progress and idempotency contract in [E0-2](E0-2.md): persist progress only after successful storage; stable source identifiers and replay/update behaviour must prevent skipped or duplicate records. Keep parsers pure where applicable (COL-004, COL-008).
- Use the existing credential/key-management boundary in [E0-6](E0-6.md), not another secret store. Retain VPN-only transport and source-limited ingest authorization if a future push path is needed (COL-002, COL-003).
- Local collection is optional and must be justified by device-only access or required filtering before transfer. Consider an extension to the existing/planned agent before introducing another process. This is not approval to extend the Phase 3 agent protocol, privileges or fixed command set; any such change needs its own scoped contract review.
- A local source remains bound to a device that can access it. Shared credentials/state do not allow arbitrary-server failover. If a future local path queues records offline, retain a defined size bound and safe replay (COL-007); do not build a general offline-sync system now.

## Redaction boundary retained

**Hub-side redaction runs after bytes leave the source device. It is not pre-transfer filtering.** SSH/SFTP encryption protects transport but does not remove sensitive content before receipt.

For a source that requires pre-transfer redaction (COL-005), filter on the source device before sending the text. A narrowly scoped source-side operation or justified local agent capability may meet that need; raw SFTP retrieval followed by hub redaction does not. If no approved source-side path can meet the requirement, leave that source import deferred rather than silently weaken its protection. Device-only access and the retained Class A protections in [E0-6](E0-6.md) also remain separate constraints.

Retain one shared redaction policy/function where applicable across imports, uploads and AI-session ingestion (RED-001). Preserve known secret-shape coverage (API keys, JWTs, bearer tokens, private keys, URL passwords and password assignments), redaction before sealing/clipping, and fixture coverage for new shapes (RED-002–004). Never place secret values or sensitive session text in logs/errors (LOG-007). Reuse existing suitable redaction code; no new redaction package is mandated without a consumer.

## Explicitly deferred

Cross-machine Claude session/file sharing, “Send to Pop!_OS” / “Send to macOS” convenience actions, a new sharing page and pseudo-cloud features are not current foundation deliverables. Revisit them only when their specific later workflow needs them; do not add them to the agent or file-transfer backlog by implication.

## Acceptance for any future scoped extension

- Name the consuming feature and selected source; demonstrate reuse of existing file access rather than a duplicate transfer/storage stack.
- Prove source selection/symlink boundaries, incremental reads and safe retry/checkpoint behaviour for that source.
- For a pre-transfer-sensitive source, prove with synthetic fixtures that required secret shapes are removed before outbound bytes leave the device; a hub-only redaction test is insufficient.
- Justify any local execution/process and obtain the required agent/ingest contract review. Prove device locality, narrow authorization and bounded buffering where those capabilities are actually introduced.
- Keep deferred sharing/UI/cloud-sync features outside the scoped change.

## Historical proposal and plan alignment

The operator's direction recorded here supersedes the **mandatory standalone-daemon build** in this issue. Relevant selection, locality, redaction, incremental-import and authorization safeguards remain. The planning documents/contracts are not changed by this issue edit: COL-001's mandatory daemon/startup requirement and the related K-E2 design need reconciliation before future implementation. No replacement process/backend/protocol is selected.
