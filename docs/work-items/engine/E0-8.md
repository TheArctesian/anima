## Approved activation and ownership behaviour — 2026-11-07

Once a feature is built into Anima, the operator can enable/disable it individually—for example Wardrobe, Library/bookshelf or Map. Enabling activates shipped functionality; it does not install, build or download a plugin. No marketplace or generalized dynamic-loader implementation is approved for the current foundation; future community extensions remain a design direction below.

### Foundation contract

- Start with a small explicit registry and ownership contracts; add entries with real implemented features. Retain the default **off** (EXT-001), each feature's data class (EXT-004), navigation identity, migration range and owned paths (K-E7/K-E8).
- Enabling makes the shipped functionality available and starts its configured imports/background work, subject to valid connection configuration and explicit prerequisites. It does not invent accounts, credentials or a new feature implementation.
- Disabling stops that feature's imports/background work and hides its pages (EXT-002), while preserving its records (EXT-003). Re-enabling reuses retained records and retry-safe progress under [E0-2](E0-2.md), not a second copy of the connection or imported records.
- Deletion is a separate explicit, confirmed action. A toggle must never delete records. Define the scope of a delete operation without silently deleting shared records owned/used by another feature.
- Declare shared capability dependencies and source consumers explicitly. Disabling one consumer must not indiscriminately stop a shared source or foundation still needed by other enabled consumers. For example, Map off does not disable location ingestion [E0-5](E0-5.md) used elsewhere. Source/connection ownership follows [E0-2](E0-2.md); shared work remains active for its remaining declared consumers. A feature toggle is not a blanket shutdown of shared infrastructure.
- Keep dependency semantics simple and explicit. Document which capabilities a feature needs and what happens if they are unavailable before accepting its enabled state. A full automatic dependency resolver or automatic enablement cascade is not designed/approved by this clarification.

### Later UI and retained delivery rules

Registry execution and ownership remain `priority: foundation`. Settings toggles, navigation groups, start page and command-palette UI remain later delivery; their intended behaviour above does not require building those screens now. Individual feature workflows remain separate.

Retain the minimal Writing [XP-03](../extensions/XP-03.md) sample inside E0 to validate contracts (ENG-010). It must not wait for an E0 completion/launch-brief gate that itself requires this sample. Retain ENG-012/013: one launch brief per extension with goal, owned paths, used contracts, sources/keys, acceptance criteria, gates and builder guidance; the operator starts later workflows from those briefs.

### Shared extension contract — accepted in principle; design first

The operator approves defining a **versioned extension manifest plus engine interface**, shared by first-party and eventual community extensions. Build Anima's own extensions against that same contract to validate it before accepting community contributions; do not design a separate first-party bypass. The current deliverable is foundational contract design, not implementation or blanket approval of a schema, API or runtime.

Work out the manifest/interface fields, ownership and dependency semantics, compatibility, updates, access/security and execution model before adopting their concrete contracts. Runtime/language, packaging/distribution, repository verification, permissions/isolation, revocation and third-party trust remain open.

The eventual direction includes an Obsidian-style searchable registry, clickable extension details and contributions from GitHub projects. Anima has no established UI-panel/design contribution framework yet: catalogue/search/details UI, UI contribution framework implementation, third-party installation and runtime execution stay later. This approval does not authorize arbitrary repository execution, a dynamic loader/marketplace implementation or blanket trust in contributed code. Existing built-in activation, retention, shared-dependency behaviour and minimal Writing validation remain.

### Acceptance criteria

- Design and review one versioned manifest/engine-interface contract for both Anima-built and future community extensions; plan first-party validation against the same contract before community contribution support. Concrete schema/API/runtime decisions still require review, and this design step does not start implementation.
- Demonstrate default-off and individual activation of implemented features; no plugin install/build/download is triggered.
- Demonstrate enable/configured-import behaviour, disable stopping feature-owned work/hiding its pages without deleting records, and re-enable using retained records/progress without duplication. UI implementation itself remains later.
- With two declared consumers of a shared source/capability, disabling one leaves the other's required work available; Map-off must not remove location evidence needed elsewhere. Demonstrate the documented unavailable-dependency policy without assuming automatic resolution.
- Verify that deletion requires a separate confirmation and respects shared ownership; validate the registry/ownership contract with minimal E0 Writing work without a circular completion gate.

**Still to settle in the contract:** per-source consumer/ownership representation, unavailable-dependency behaviour, in-flight work/cancellation at disable, and shared-data deletion boundaries. No backend, general dependency solver or broad spec/contract approval is selected here. Existing requirements and programme gate below remain; repository docs/contracts are unchanged by this issue edit.
