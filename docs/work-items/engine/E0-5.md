## Approved foundation: places, location ingestion and event context

Time and location are foundational capabilities, not just later Map presentation. Retain shared places and ingest location evidence from the operator's phone or chosen connected location provider. Use it to associate relevant events, including SSH/SFTP transfers, with the appropriate time/location evidence through stable references.

Keep this foundation independent of Map UI, new sharing screens and a speculative connector catalogue. The exact provider named verbally as “Darwich” is unverified (possibly Dawarich); confirm the provider and supported integration before selecting or building it. No integration is selected by that guess.

### Shared places and location observations

- Retain places with name, centre, radius, category, icon and aliases; child places apply radius only at the top level (PLC-001/002). Operator names take precedence over geocoder names (PLC-003).
- Other domains refer to a stable `PlaceId` rather than copy the place. Preserve merge/split reference handling, refusal to delete a referenced place without replacement, and links between Anima sites and places (PLC-004–006).
- Ingest only the operator's chosen phone/provider source through the shared connection/import contracts in [E0-2](E0-2.md). Preserve provider/source identity, sample identity, original observed timestamp, coordinates/place evidence and accuracy/uncertainty where available. Missing accuracy or time must remain unknown, not appear exact.
- Follow [E0-4](E0-4.md): use consistent Unix event instants with its documented wire unit/precision once chosen; preserve original source/sample time and distinguish ingest time. Do not replace historical evidence with the latest current position.
- Define event-time matching, maximum staleness, uncertainty and any place-inference rules before implementation. A nearest-time/stale/inferred match must be distinguished from a contemporaneous observation or explicitly confirmed place; it must not silently become confirmed location. No numerical tolerance/staleness threshold is approved here. Missing evidence remains unknown.

### Event association and SSH/SFTP boundary

- Record one transfer event with a stable event ID at the existing SSH/SFTP transfer boundary: source device/location evidence, destination device/location evidence, and initiating actor/client. Add separate operator-location evidence only when available. Both devices may reference that same event ID in their activity views; do not create duplicate domain events. Use [E0-4](E0-4.md) reference semantics rather than copying source records into a separate timeline/location store. This is intended behaviour, not a claim that current transfer logs already capture it; no new UI is implied.
- Keep operator location distinct from source-device, destination-device/site and file-associated location metadata. These are separate roles with their own provenance/uncertainty; a file's embedded GPS metadata is not proof of the operator's position or its current storage site.
- Example: an operator working at home fetches a file from the office PC. One event references the office PC/Office as source and the home machine/Home as destination, with the initiating actor/client separately identified. The source/destination place evidence comes from configured or reported device/site information; pinging a host does not establish its physical location. The location of a server that stores/ingests the event is not the event’s physical location.
- Separately, an operator in a café can transfer between two machines at home. Record the café as operator-location evidence only if supported at the transfer time; independently reference the machines' known sites. Do not label the transfer “from Home” based on operator location, or infer the operator is at Home from the device sites.
- Reuse the current SSH/SFTP transfer mechanism. This issue adds scoped event/context recording where meaningful, not another transfer stack, mandatory collector or broad file harvesting. [E0-3](E0-3.md) retains reuse-first, device-local and pre-transfer-redaction boundaries.

### Person, machine and agent activity attribution

Machines at different sites may work on different things simultaneously, including autonomous/background agent work, while the operator has a separate location and activity. Track person-level and per-machine event context without treating every event in the personal network as a direct human action.

- Distinguish human interaction from autonomous agent/system activity. Preserve the executing actor (human, agent or system), execution device/site, and initiating actor/device where known; an operator initiating an agent task does not make every later agent action a direct human interaction.
- Correlate person and device activity through explicit session/interaction evidence and its timestamps, using stable references to that evidence. Device ownership, an arbitrary machine event, a ping or location proximity alone does not establish that the person was actively using that machine. Preserve unknown/uncertain attribution and its provenance rather than assume an actor or exclusive active device.
- Reuse existing or specifically approved evidence when available. This records intended attribution semantics, not an implemented presence detector, activity-surveillance capability or approval for a new collector/agent protocol. Screens remain later.

### Attachment/file safeguards retained

Retain the intended shared attachment store/reference contract, not a general cloud drive: content-hash storage in the named Docker volume with database metadata (FIL-001); sealing under the record's data class (FIL-002); removal of EXIF GPS from displayed photo copies, retaining a location field only with operator permission (FIL-003); archive deletion removing its derived records (FIL-004); and the existing 256 MB upload limit with streaming rather than whole-archive buffering (FIL-005).

Use stable attachment references and existing suitable file/storage capabilities where possible. New location/event context does not authorize copying every transferred file into the attachment store or collecting its contents. Personal-record/Class A protections in [E0-6](E0-6.md) remain.

### Extraction/vision ownership retained

Shared vision-model discovery, downloads, runtime and inference routing remain in [C1 #34](../compute/C1.md). Class A extraction stays on-client (VIS-002); optional per-extension hosted processing permission remains [OD-E4](../decisions/OD-E4.md), not granted here (VIS-003).

## Later work

Map UI [XP-01](../extensions/XP-01.md), History UI [XP-07](../extensions/XP-07.md), “send to device” actions, cross-machine session/file-sharing conveniences, new sharing screens and generalized pseudo-cloud features remain later. Location ingestion and event-time/context contracts do not wait for those screens.

## Acceptance criteria

- Document the confirmed chosen provider and a minimal ingestion contract; demonstrate retry-safe sample ingestion retaining provider identity, original observed/ingest times and available accuracy/uncertainty. Do not build an integration from the guessed provider name.
- Associate a transfer event with stable references to the appropriate time/location evidence. A late-imported sample and a different latest position must not rewrite the event's original time or silently substitute current location.
- Demonstrate the home-to-office-PC fetch as one event referenced by both devices, with source Office, destination Home and initiating actor/client; retain their configured/reported location provenance. Do not treat the ingest server or host reachability as physical-location evidence. Demonstrate the café/home scenario with operator and source/destination roles kept separate. Demonstrate unknown, stale and nearest-time inferred evidence without presenting it as confirmed; document the matching/staleness policy before acceptance.
- Preserve place merge/reference integrity and relevant attachment, EXIF-permission, sealing and extraction-confirmation safeguards. Do not duplicate domain/source records or import transfer contents merely to attach event context.
- Keep concurrent autonomous machine/agent events distinct from human interaction; demonstrate evidence-backed person/device correlation and unknown attribution without inferring active use from ownership, events, ping or proximity alone.
- Demonstrate meaningful transfer context using existing SSH/SFTP; no new transfer stack, Map/sharing page or generalized sync layer is required for this foundation.

**Open design choices:** exact location provider/integration, event/sample matching tolerance and staleness/uncertainty policy, plus the Unix precision/portable-reference choices tracked in [E0-4](E0-4.md). No backend or distributed replication architecture is selected.
