## Approved compute foundation scope — 2026-11-07

### Three distinct layers

1. **Hardware signals and compute decisions.** Reuse GPU inventory/readings from Phase 3 WP-51/WP-54 and its shared `agent`/`agent-core` foundation. Those metrics do not already provide compute eligibility, placement or scheduling: add those decisions here using available capability, memory and device-policy inputs. No exact runtime choice or automatic model-selection policy has been settled.
2. **Per-machine model setup.** Downloads, storage and runtime operation belong together: check whether a model/variant fits available memory, verify and resume approved downloads, operate loopback-only runtimes and recover/report runtime crashes. Fit checks, download reliability and supervision are supporting parts of setup, not separate product features. Do not assume a model fits merely because a GPU is present. Runtime/model compatibility must be explicit.
3. **Unified registry and routing.** `ai.anima.ing` exposes the model registry and private authenticated serving for other projects, including a caller's chosen compatible model and machine. Validate the selection or return a clear incompatibility/unavailability reason; do not silently imply an approved automatic selection policy. Streaming text is part of serving. Visual model/machine pickers and Models/Chat/Compute screens are later delivery, not foundation acceptance requirements.

Serving models on different machines is ordinary fleet serving. Splitting **one** model across heterogeneous Macs/NVIDIA/other frameworks is separate research in [C4](C4.md)/[C6](C6.md), with [leyten/shard](https://github.com/leyten/shard) as the existing reference. It is not required for normal C1 serving.

### First-release endpoint authentication

- Use **one shared API key for all models** at `ai.anima.ing`. Per-project credentials and per-model restrictions/allowlists are deferred and must not appear in v1 acceptance.
- Keep the endpoint private and authenticated. The router authenticates incoming calls; the central VPS vault in [E0-6](../engine/E0-6.md) owns key storage/distribution and its protected-cache lifecycle. Keep shared-key rotation/revocation, with the transition/invalidation behaviour explicitly defined before implementation.
- This is router endpoint API-key scope only. It does not merge or relax agent enrolment, node-token or compute-command authorization boundaries. Retain existing download verification, runtime isolation, security review and no prompt/output logging protections.

### Desired model families; compatibility and delivery must be staged

The operator approves the following desired capability taxonomy/architecture coverage, inspired by model offerings encountered through Unsloth/Ollama:

- **Text:** chat, coding, reasoning, translation, summarization and text classification; structured extraction/entity tagging (token classification).
- **Image:** generation, editing, upscaling and image classification.
- **Video:** generation, editing, understanding and video classification.
- **Audio/music:** music and sound-effects generation, audio generation/understanding, audio classification and audio-to-audio transformation.
- **Speech recognition:** transcription and spoken translation.
- **Speech generation:** text-to-speech and conversational voice.
- **Vision/document capabilities:** image understanding, OCR, document-field extraction, table/document question answering and visual document retrieval; object detection, image segmentation/background masks, depth estimation and keypoint/pose detection.
- **Search representations:** embeddings and reranking for semantic search.
- **Tabular:** classification and regression.
- **Reinforcement learning:** catalogue/schema capability coverage for policies; this does not approve immediate RL training infrastructure.
- **Later target coverage:** 3D/object/mesh/scene generation.

These are distinct capabilities, not proof that every model/runtime from Unsloth/Ollama works, a runtime/backend selection or a dependency decision. They are not all first-release deliverables; concrete model/runtime compatibility, modality contracts and implementation stages still need design and validation.

The additional task tags above are operator-approved desired catalogue/schema coverage, checked against the [official Hugging Face task catalogue](https://huggingface.co/tasks). Treat subtypes as capability tags within the existing architecture, not separate serving layers. Hugging Face remains the already-planned model download source with verification/resume; no new provider authentication is requested here.

Track **catalogued/downloadable**, **downloaded**, and **validated for a specific runtime/hardware combination** separately. Availability for download is not evidence of executable compatibility. Catalogue capabilities and compatible model/variant/runtime/hardware combinations explicitly. Stage implementation and publish only validated capabilities. Non-text generation may need asynchronous job, progress and artifact/result contracts; speech/conversational voice may need audio/real-time contracts, while search representations need embedding/reranking request/result contracts. Design the modality boundaries rather than imply text streaming covers them. The taxonomy records approved desired scope, not implementation approval or blanket compatibility; 3D remains a later target.

Shared vision serving remains owned here for extraction contracts [E0-5](../engine/E0-5.md) and separate Wardrobe/Library consumers; existing Class A/on-client and hosted-permission boundaries below remain.

### Acceptance and open design work

- Demonstrate the extra compute eligibility/placement/scheduling boundary separately from reused Phase 3 metrics. Validate per-machine fit and compatibility, verified/resumable downloads and crash recovery without duplicating the agent foundation.
- Demonstrate a Mac and Linux node's validated models through the unified registry, explicit compatible model/machine selection and streaming text. Refuse unauthenticated calls; the one shared v1 key works across all validated models without per-model/project restrictions. Verify rotation/revocation and the no prompt/output/image logging protections.
- Before claiming a non-text family supported, agree its request/job/progress/artifact contract and validate that model/runtime end to end. Record family-specific implementation stages without treating desired coverage as already implemented. UI is not required for these checks.
- User-reported target hardware is a Mac M4 32 GB, this Mac M5 48 GB, and a Pop!_OS desktop with an A6000 and unspecified i9. These are not inspected inventory; do not assume an A6000 VRAM variant. Confirm hardware through [OD-C1](../decisions/OD-C1.md) before fit/runtime decisions; [OD-C1](../decisions/OD-C1.md) is not changed here.

**Plan alignment required:** the older RTR-004 key/model-allowlist requirement and “API keys with permitted models” checklist below conflict with the approved one-shared-key v1 scope and are superseded for this issue's v1 acceptance. Align the related SEC-C-003/router-key wording with [E0-6](../engine/E0-6.md) while preserving separate node/agent credentials. SEC-C-002/004 listener/ACL assumptions still need alignment with R-084/MET-020; this is not approval to open an agent port. Level 1, first part. Each compute node runs the runtime that suits its hardware, pulls models, and serves them through the router at `ai.anima.ing` with the OpenAI API.

- [ ] `anima-agent` and `compute-agent-core`: enrolment, node token, fixed command list, supervision, reports every 15 s
- [ ] Capability inventory and device policy (disk share, mains power, drain)
- [ ] Runtime choice: MLX-LM on Macs, vLLM on NVIDIA when the model fits, llama.cpp elsewhere; loopback only
- [ ] Model library: approved Hugging Face orgs, variants with SHA-256, `name:tag`, aliases
- [ ] Pull: hub picks the variant, agent downloads from Hugging Face, verifies, resumes
- [ ] Fit estimate (pure function)
- [ ] Router: `/v1/models` with Anima fields, chat, completions, embeddings, responses, routing, streaming
- [ ] API keys with permitted models; no prompt logging
- [ ] `ai.anima.ing` on Headscale DNS with a DNS-01 certificate (needs OD-C7 and operator confirmation, VPS-005)
- [ ] Compute page with API key management, compute badge
- [ ] Measure the added delay of the VPS router (OD-C5)
