## Approved foundation: configurable loading and request readiness — 2026-11-07

C1 [C1](C1.md) supplies fit/runtime compatibility, model copies, downloads and ordinary fleet serving. This issue adds configurable loaded-memory lifecycle and request scheduling/readiness; it does not duplicate model setup, add split-model/sharding implementation or require Models/Chat/picker screens first. Retain [C1](C1.md)'s approved capability taxonomy and one shared v1 key for all models.

### Loading, unloading and memory capacity

- Make idle-unload timeout configurable and allow the operator to pin desired models. Do not impose one universal fixed idle timeout. Distinguish downloaded files, loading copies, loaded/ready copies and active work; unloading releases GPU/system runtime memory while retaining downloaded model files.
- For an unloaded compatible model, load it before generation. Progress-aware callers opt in to loading/readiness status and asynchronous result handling through a supported contract; ordinary calls wait for their normal compatible result within the applicable timeout/deadline. If capacity is temporarily unavailable, expose waiting/queued status only through the supported opt-in mechanism, not generated output.
- Track live memory reservations and concurrent requests, including in-progress loads and active generation. When a larger requested model needs room, unload eligible **idle** models, for example by least-recent use. An idle pinned model may yield memory: pin means a **keep-warm preference**, not an unevictable memory reservation. Never unload a model with active work, silently kill active jobs or delete downloaded copies to free runtime memory.
- Preserve the pinned model’s desired loaded state when it yields. After the competing request completes and capacity allows, restore it without thrashing or starving waiting demand. The exact restoration/fairness policy remains open.
- Recheck fit/capacity through [C1](C1.md)'s model/runtime/hardware foundation. Distinguish temporary occupied capacity from a model inherently too large for the selected runtime/hardware. If safe eviction cannot make room, follow the caller-selected waiting policy (wait/deadline versus fail-fast), reporting capacity waiting or a clear refusal through the supported contract; do not silently override an explicitly selected machine or choose a different model.

### Progress is not generated content

Expose caller-selectable wait/deadline versus fail-fast behaviour through the endpoint; do not impose only a fixed waiting policy. Exact extension field names and default limits are not chosen. Design status for stages such as queued, loading, ready, running and failed as applicable; exact state names/transitions remain contract work. Define timeout, cancellation, load/generation failure and capacity-wait handling, including cleanup of reservations and outcomes visible to the caller.

Progress-aware callers opt in to “loading model” and readiness before the result. Ordinary OpenAI/Ollama-compatible calls wait for their normal protocol-compatible result, subject to the supported timeout/deadline mechanism. Do not inject fake loading text into generated output, invent unsupported stream chunks or send arbitrary extra HTTP responses. Validate each protocol’s status/result behaviour; no Anima wire schema is finalized here. Non-text jobs use the modality-contract boundary in [C1](C1.md) rather than assume every result is a text stream.

**Reusable async design candidate:** official OpenAI [Responses background mode](https://developers.openai.com/api/docs/guides/background) documents `background=true`, queued/in-progress lifecycle, retrieve/poll/cancel and background streaming/resumption. Consider that Responses-style lifecycle instead of inventing incompatible output content. Anima-specific GPU capacity wait/deadline and idle-pin eviction controls are **local API extensions**, not assumed OpenAI/Ollama standard fields. The [Chat Completions reference](https://developers.openai.com/api/reference/resources/chat/subresources/completions/methods/create) does not document those local GPU controls; `service_tier` is not a local eviction/wait/deadline policy. Exact extension names, limits and compatibility mapping still require design.

### Foundation acceptance; UI later

- Demonstrate configurable idle timeout and keep-warm pins: an idle pinned model can yield memory, downloaded files remain, active work is never evicted, and its desired loaded state is restored after competing work when capacity/fairness permit.
- Exercise simultaneous requests/loads with live reservations: a larger compatible request can reclaim eligible idle memory without overcommitting or killing another job. Demonstrate caller-selected wait/deadline and fail-fast behaviour when occupied capacity cannot safely be reclaimed, versus a clear inherent-fit failure. Test that pin restoration does not thrash or starve waiting demand.
- Demonstrate ordinary compatible calls waiting for real results and opt-in progress-aware calls using supported loading/readiness status, with timeout/cancel/failure cleanup and no invented model-output text. Preserve explicit model/machine selection and validate compatibility-client behaviour against the chosen protocol contract.
- Models, Chat and model/machine-picker UI remain later, including the existing page requirements below. Their completion is not a gate for accepting this lifecycle foundation. Preserve alias behaviour and the existing Ollama endpoint requirements.

**Plan alignment/open choices:** reconcile FIT-020–022 and RTR-031 with configurable policy, live reservations and asynchronous readiness. The plan's 15-minute default is existing planning context, not a mandatory universal timeout; pin granularity, restoration/eviction fairness, queue bounds, exact local waiting-policy extension fields/default limits, Responses-style lifecycle adoption and timeout/cancel semantics remain to be designed. Do not infer an automatic machine/model selection policy. Repository docs/contracts are not changed by this issue edit.
