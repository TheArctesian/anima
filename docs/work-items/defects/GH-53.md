**Found:** 2026-11-07, O-3 (VNC to a Linux desktop), Mac app → `pop-os` running wayvnc 0.10.2.

**What happens:** the session toast says "The gateway reported an error and closed the VNC session". guacd logs only `ERROR: Unable to connect to VNC server.` The real cause, from wayvnc's side, was a rejected login: wayvnc offers `rsa-aes256, rsa-aes128, apple-dh, 3des`; guacd's libvncclient picks Apple DH, which sends the stored VNC user name. R-079 pre-fills that user name with this computer's OS user (`okita`), while wayvnc had no `username` configured (expects empty), so it rejected the login. Setting `username=okita` in wayvnc's config fixed it at once ("User "okita" authenticated").

**Problems:**
1. The operator cannot tell a login failure from a network failure: both read "Unable to connect" / "the gateway reported an error".
2. For a Linux VNC server, the pre-filled user name (R-079) can silently break login with servers that check it (wayvnc with apple-dh).

**Suggested:**
- Map guacd's authentication failures to a credential error that opens the credential prompt (GW-015) instead of the generic toast, if guacd exposes the distinction (status 0x0301/0x0303 vs 0x0200).
- For Linux devices, consider not pre-filling the VNC user name, or say in the VNC section hint that it must match the server's user (wayvnc `username`).

## Check of 2026-11-17

State: corrected. Problem 1 was corrected before this check; problem 2 is corrected in the commit that adds this section.

- **Problem 1 (a refused sign-in looks like a network failure): already corrected.** Since 193342fb (2026-11-14, one-click S2 T6) the gateway of Anima (`crates/anima-gateway`) is the VNC client. When the device refuses the sign-in, it sends `error` with status 0x0301 (`crates/anima-gateway/src/session/opening.rs` line 160; test `a_refused_sign_in_ends_the_session_as_unauthorized` in `crates/anima-gateway/tests/it/session.rs`). The hub ends such a session as `AuthFailed`, "The device refused the VNC sign-in." (`crates/hub/src/fleet/sessions/tunnel/gateway.rs` `error_cause`, `end/cause.rs` line 193), and the client shows "The device refused the sign-in, or no credential is stored." (`apps/client/src/lib/sessions/ending.ts` lines 34 and 57). A device that is not there gets a different status (0x0207).
- Limit: a hub that sends VNC to guacd (`other_gateway` with `passed`) keeps the old text, because guacd gives one status for both failures.
- **Problem 2 (the pre-filled user name): was present, corrected.** `SetupFlow.start` stored the OS user of this computer as the VNC user name on macOS and on Linux (`apps/client/src/lib/devices/screen-sharing/flow.ts` line 42). Now `screenSharingUser` (`setup.ts`) gives the OS user only on a Mac; on Linux the flow stores no name, and a stored name stays as before. Test: "GH-53: this computer on Linux has VNC turned on with no username" in `setup.test.ts` (it failed before the change).
- For the operator: R-079 says "the username pre-filled with this computer's user when the device is this computer". This correction makes that true only on a Mac. The text of R-079 is not changed; the operator decides if it gets an amendment.
- Not changed: the hint of the VNC section ("Optional. macOS Screen Sharing needs one."). It already says where a name is necessary.
