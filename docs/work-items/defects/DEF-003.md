## What was seen

In the application, signed in to his hosted hub, the operator started Connect GitHub. The browser opened `https://hub.anima.ing/connect/github` with a one-time ticket. His words: "the setting up via git goes to here ... so can't connect". `hub.anima.ing` is the old hub on the VPS, which he no longer uses. His hub is reached only through the link, at `http://127.0.0.1:<port>` on his Mac.

The ticket is not written here, and must not be written in a document, a commit or a log.

## Cause, from the code

Read in the code of `dev` at `3353f648`. Not run.

- The hub makes the address, not the application. `crates/hub/src/engine/sources/graphql/registration/view.rs` takes `config.public_origin`; `registration/words.rs` adds `/connect/github`. The application opens the address that the hub gives (`apps/client/src/lib/sources/connect/`). A saved address in the application has no part in it.
- `crates/hub/src/config.rs`: `ANIMA_PUBLIC_ORIGIN` has the default `https://hub.anima.ing`. A hub whose environment does not set the variable thus says that its public address is the old hub.
- The hub of the one-click installation does not set it: `crates/anima-local-hub/src/members.rs` says "ANIMA_PUBLIC_ORIGIN and ANIMA_PROBE_DENY keep the hub's defaults". No file of the private pool repository names the variable (looked for by its name on 2026-11-19; nothing of that repository is copied here), so a hosted hub has the default too.
- The same origin goes into the manifest of the GitHub App that the hub makes (`crates/providers/github/src/registration/manifest.rs`): `redirect_url`, `setup_url` and the webhook address. GitHub sends the browser back to those addresses.

Which case this is: the base address is a default that is wrong for each hub that is not at `hub.anima.ing`. But a correct value does not exist for a hosted hub. The flow needs one address of the hub that the browser of the person can open and that the hub knows before the flow starts, with `https`: the cookie of the flow is `__Host-anima-connect` with `Secure`, and the page `POST /connect/github/open` compares the header `Origin` with the public origin. A hosted hub has no public address; each computer reaches it at a local port that the application chose. Thus the flow cannot work for a hosted hub, or for a hub of the one-click installation, as it is designed. It is a design question: HM-D17.

## Effect

- On a hosted hub and on a local hub of the one-click installation, GitHub cannot be connected. Each function of Projects that needs the GitHub App is not available.
- The one-time ticket of the attempt goes, in the address, to a server that is not the hub of the person: `hub.anima.ing`. For each person of the hosted mode that is a server of the business. The ticket is valid only at the hub that made it, for 5 minutes and for one use, so the other server cannot use it; but a value that the contract keeps between the client, the browser and the hub leaves them.
- If the old hub is turned off, the person sees a browser error with no explanation.

## Seen again, 2026-11-19

The operator, on a local build of `main` at `132c24dc` (0.8.16), signed in to his hosted hub; first-hand to the orchestrating session, relayed. Settings > Integrations > GitHub showed "Opening GitHub in your browser." with "Continue in browser". The browser page had the title "Connect GitHub to Anima.ing" and said "This link was already used or has ended. Go back to Anima.ing and press Connect GitHub again." So the one-time link still went to the server at the default public origin, which does not know it. Each press made a new one-time link and sent it there.
