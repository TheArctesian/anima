## What was seen

The two numbers do not agree. 15 minutes of 24 hours is 1.04 %, so a device that is down for 15 minutes or more has at most 98.96 %. 99.81 % is about 2.7 minutes.

## Cause, from the code

Read in the code of `dev` at `aa7114bb`. Not run against a real hub.

- The hub is not the cause. It counts the up, the degraded and the down results of each check of the device in the last 24 hours, from rows that it writes in the same transaction as each result (`crates/hub/src/fleet/checks/uptime.rs`, `crates/hub/src/fleet/checks/store/uptime.rs`, `store/beats.rs`). No step of it is late.
- The client reads `uptime(window: DAY)` only when it loads the list (`apps/client/src/lib/devices/api.ts`). A live change gives the list a new status and new check results, and not a new uptime: `applyStatus` in `apps/client/src/lib/devices/list.ts` changes `status` only. Thus the number is of the time of the last load, and the red marks beside it are of now. A list that was loaded about 3 minutes after the device went down shows 99.81 % until the page loads again.
- A second fault was in the same row and is corrected on the branch `ui/devices-list-layout`: "15 min" was the age of the oldest of the 50 results that the client keeps, not the time since the device went down. It now reads "over 15 min" when no kept result is up (`sinceOf` in `apps/client/src/lib/devices/list/look.ts`).

Not known from the code: the interval of the checks of that device, and when the operator loaded the page. If the number stays at 99.81 % after a new load, this cause is wrong, and the next thing to look at is a check that records Unknown results, which the hub does not count.

## To do

- [ ] The list must get the uptime of a device again when its status changes or when a result of a check that is not up arrives, or must ask for it at an interval. The hub API already gives the value; no contract changes.
- [ ] A test that proves that the number changes with no new load of the page.
