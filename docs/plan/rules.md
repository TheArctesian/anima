## 10. Rules for plans and progress

These rules apply to each person and each agent (operator, 2026-11-15).

- **PLN-001. One register.** Section 9 is the only list of plans. Do not build from a document that is not in it.
- **PLN-002. No plan without a row.** Do not make a new plan, proposal or task breakdown unless the same commit adds its row to Section 9.
- **PLN-003. Each plan has a parent.** A new plan must name the row of Section 4 that it serves. If no row applies, ask the operator for one first.
- **PLN-004. Change a plan before you make a new one.** If a plan in Section 9 owns the concern (Section 5), change that plan.
- **PLN-005. One standard.** Each plan obeys the writing rules in Section 0 of the design specification. Each plan has a title, a version, a date and a status. The line below its title points to Section 9.
- **PLN-006. Tasks hold their state.** A plan or a task breakdown that has tasks must have a table with one row for each task. The row gives the state and the commits.
- **PLN-007. The words for a state.** The state of a plan or a proposal starts with one of these words. Each word says what a session can build.
  - Draft: the operator approved nothing. Build nothing. A measurement or a prototype that is a record in `research/` is permitted.
  - Direction decided: the operator approved the direction, with a ruling. Build only the task that a ruling names. A proposal stays in `proposals/`.
  - Approved: the operator approved the requirements, with a ruling. The document is a plan in `plans/` (PLN-018). A requirement that has no ruling is marked in the plan and is not built.
  - In progress: an approved plan with a task that is started. Done: each task is done, with evidence (PLN-009). Parked and Withdrawn: build nothing.
  - Not checked: no person or agent compared the document with the code. Build nothing until it is checked.

  A task is Not started, In progress, Done or Cancelled. A task that is In progress and has no claim (PLN-022) is not free: find its branch or ask the operator, then claim it or set it to Not started.
- **PLN-008. Progress moves with the work.** Change the state of a task in the commit that does the work, or in its merge. Change Section 9 when the state of a plan changes.
- **PLN-009. A state needs evidence.** "Done" must name a commit, an acceptance record or a ruling of the operator. Do not write "Done" for work that waits for a live check.
- **PLN-010. Records are not plans.** A report, a log, a procedure or a review must not add a requirement. Put the requirement in its owner (Section 5).
- **PLN-011. A plan on a branch.** A plan that is only on a branch is not a plan. Merge it with its row before work on it starts. A plan, a contract and a ruling merge to `main` before the code that depends on them (operator, 2026-11-18, R-155). A session that finds a gap in a plan while it builds changes the plan, merges that change to `main`, and then builds on.
- **PLN-012. No second store.** Do not keep a plan, a task, a decision, a defect or a deferred item in a GitHub issue, a project board or a label (operator, 2026-11-16, R-119). A new work item or a new defect is a document in [work-items/](../work-items/README.md) with a row in its index. A deferred item is a line in [deferred.md](../deferred.md). An open decision is a row in the "Open decisions" section of its plan. If a person outside the project opens an issue, move its content to a document and close the issue with the path of the document.
- **PLN-013. Plan first.** A session that builds must start from a plan (operator, 2026-11-16: "The coding session should plan for or at least read from the plan and build or update the plan"). Before it changes code, the session must do one of these:
  1. Find the plan that owns the work (Section 5, Section 9), read it, and build from it.
  2. If that plan does not include the work, change the plan first (PLN-004). Then build.
  3. If no plan owns the work, write a proposal first, with its row (PLN-002, PLN-003). A short proposal is sufficient: the goal, the requirements with identifiers, and the open decisions. Build after the operator approves it or names the task in a ruling (PLN-007); the instruction of the operator to build is such a ruling, and it gets a number (PLN-021).

  If the build must be different from the plan, change the plan in the same commit. Change the state of the task in the commit that does the work (PLN-008). A correction of a defect that adds no function and changes no requirement needs no plan; it names the requirement that it corrects.
- **PLN-014. One list of human checks.** A check that only a person can do (a real machine, a real account, a real network) has an entry in [need-human-testing.md](../need-human-testing.md) (operator, 2026-11-16). A new check gets an entry `HT-nnn` with its steps, in the commit that builds the function. A check whose steps are in an older document has a row in the section "Checks that other documents hold"; the row names what the check blocks and holds its result. A task that waits for a check is not Done until its entry or its row says Passed (PLN-009). `AGENTS.md`, section "Human testing", gives the rules for agents. An entry or a row can have the state "Deferred" (operator, 2026-11-18, R-169): the check is put aside because it cannot run now, for example a check that needs the hub on the VPS or its VPN while the operator uses only the hosted hub. Only a ruling of the operator sets Deferred. The entry then gives the reason and the number of the ruling. A deferred entry is not deleted and is not Passed: a task that waits for it is not Done (PLN-009). A ruling, or the operator, sets it to Open again when the check can run.
- **PLN-015. No line limit for planning documents.** The size limits of `AGENTS.md` apply to code only (operator, 2026-11-16). Do not divide a specification, a plan or a proposal to make it shorter. Divide a document only when it holds two subjects that have different owners, and keep its identifiers and its section numbers.
- **PLN-016. One entry, one job, one owner.** These three rules keep the documents easy to find and hard to misuse (operator, 2026-11-16).
  1. One entry. [work-plan.md](../work-plan.md) is the entry point. A reader must be able to get from it to each planning document through a list: the register, the index of the work items, or a link in this folder.
  2. One job. A document has one job: a map, a specification, a plan, a proposal, a task breakdown, a list or a record (Section 9 gives the kinds). Do not add a second job to a document. Put the text in the document that has that job.
  3. One owner. One document holds each fact. One document defines each requirement identifier (Section 5). The register holds the state of a plan. The index of the work items holds the state of an item. [need-human-testing.md](../need-human-testing.md) holds the result of a check. A different document points to the owner; it does not copy the fact. A definition is a bold identifier with a full stop at the start of a line (`**DEV-001.**`). A note about a requirement of a different document uses a colon (`**DEV-001:**`) and does not define it.
- **PLN-017. The documents gate.** `bun run quality:documents` is one of the gates (`bun run gates`). It fails when a relative link does not resolve, when a plan, a proposal or a task breakdown has no link in the register (PLN-001), when a work item has no link in its index (PLN-012), when a mockup has no link in its index (PLN-019), when the header of a plan has no kind or no state, or when the table of Section 9 does not agree with the headers (PLN-020), or when a second document defines a requirement identifier (PLN-016). `quality/duplicate-identifiers.txt` lists the identifiers that have two definitions. That list can only get shorter: the gate fails when an identifier of the list has one owner. The gate also fails when the register has no generated list, when a plan has no evidence, when two rulings have one number (PLN-021), when a claim is not complete (PLN-022), when a mockup is behind its screens (PLN-019), and when the operator queue does not agree with the documents (PLN-023).
- **PLN-018. The path of an idea.** Work goes through these stages in this order (operator, 2026-11-17). A stage must not be skipped, but a stage can be short.
  1. Idea. One folder for each idea in [ideas/](../ideas/README.md). It has no requirement and no row in Section 9. Do not build from it. The commit that makes it a proposal, or that drops it, deletes the folder.
  2. Proposal. One document in `docs/proposals/`, with its row in Section 9 (PLN-002) and the row of Section 4 that it serves (PLN-003). It gives the goal, the requirements with identifiers, and the open decisions. Each review round raises its version and records what the operator decided. A proposal is ready for approval when its table of open decisions gives, for each row, one question that the operator can answer with yes, no or one choice, and a recommendation. A proposal is a draft: build from it only the parts that a ruling names (PLN-007).
  3. Plan. When the operator approves the proposal with a ruling, the same commit moves the document to `docs/plans/<name>-plan.md`, changes its title and its status, changes its row in Section 9 to "Plan" with the ruling, and corrects each link. A requirement that has no ruling stays in the plan and is marked as not approved.
  4. Contract. If the plan changes an interface that the parts share, the contract in `contracts/` changes with a ruling (CON-001) before the build.
  5. Tasks. The plan, or its task breakdown, holds one row for each task (PLN-006 to PLN-009). A session builds from the task (PLN-013).
  6. Check. A function that the gates cannot prove gets its entry in [need-human-testing.md](../need-human-testing.md) (PLN-014). The task is Done after the operator sets the entry to Passed.
- **PLN-019. A mockup agrees with the application.** Each mockup has a row in [mockup/README.md](../mockup/README.md) with its owner plan, the screens that it shows, its state and the commit at which it was compared (operator, 2026-11-17). A commit that changes the layout of one of those screens changes the mockup in the same commit, or writes the difference in the row. A difference is a defect. A mockup takes its values from the design tokens. A mockup of an idea is in the folder of the idea until the idea is a proposal. The documents gate fails when a mockup in the state Built names no commit of comparison, or when a layout file (Svelte or CSS) of one of its screens has a commit after that commit (PLN-017).
- **PLN-020. The header holds the state; the register is generated.** Each plan, proposal and task breakdown starts with a header between two `---` lines: `kind:`, `state:` (it starts with a word of PLN-007) and `evidence:` (PLN-009), each on one line (operator, 2026-11-17). This header is the only place that holds the state of the document. `bun run quality:register` writes the table of Section 9 from the headers. To change a state, change the header and run the command, in the commit that does the work (PLN-008). Do not write the state of a plan in a second document; point to Section 9.
- **PLN-021. One log of decisions, one series of numbers.** [rulings.md](../rulings.md) is the only log of decisions (operator, 2026-11-17). A decision of the operator that approves or changes a requirement, a contract or a plan gets the next free number `R-nnn` there, in the commit that records it. A table of open decisions in a plan (`OD-...`) holds the question and the recommendation; when the operator decides, its row gives the result and the number of the ruling. A branch takes its number when it merges: if `main` has the number, the branch takes the next one. The gate fails when two rulings have one number.
- **PLN-022. A session claims its task.** A session that starts a task writes one file in [claims/](../claims/README.md) and pushes that commit to `main` before it builds (operator, 2026-11-17: "a light commit to the docs on main when it starts the work"). The file names the task, the plan, the machine, the coding agent, the branch and the day. The machine is not planned: the session writes the machine that it runs on. A session does not take a task that a claim holds. The commit that merges the work deletes the claim. A claim is old when its branch has no new commit for 3 days; check before you take its task. The gate fails when a claim is not complete or when two claims hold one task. The steps are in [claims/README.md](../claims/README.md): the session makes the claim commit in a small worktree of `origin/main`, and its branch starts from or merges that commit, so that the branch holds the claim and the merge deletes it. The claim commit can also hold the row of a new task.
- **PLN-023. One queue for the operator.** [operator-queue.md](../operator-queue.md) lists what waits for the operator: the rows of Section 4, the open decisions, the documents that wait for an approval, and the open human checks (operator, 2026-11-17). It is generated by `bun run quality:register` and it holds no fact of its own. A session does not only tell the operator in a chat that something waits: it writes the row in the owner document (an open decision in the plan, the state in the header, an entry in need-human-testing.md) and runs the command. In Section 4, a task for an agent has a link to the plan or the work item that holds it. The gate fails when there is no link, and when the linked document has a state that does not permit a build (PLN-007). A decision is open in the queue until the last cell of its row starts with "Decided", "Not a decision", "Withdrawn", "Closed" or "Superseded": write the result there.

A task list that an agent keeps for one session is not a document. These rules do not apply to it.
