## Decisions

- **G-1 Playback proof uses real guacd output.** T1 builds its stream from WP-47 T1b's guacd 1.6.0 VNC
  captures (`sessions/tunnel/tests/fixtures/guacd-1.6.0-vnc-join-opening.guac` without `ready`, then the
  `...-owner-left.guac` frames): the instructions the hub relays to the owner after `ready`, which K4 §11 says
  are exactly what is recorded (the BMP guard is the identity on that ASCII). T8 proves the tee writes exactly
  the relayed instructions, so the chain real guacd → tee → player is covered by two tests. The vendor file is
  imported, never changed. The DOM canvas is the only fake (jsdom has none); a real-engine spec beside it is
  optional and outside the gates.
- **G-2 STREAM by hand, no new crate.** `aead` 0.6 has no `stream` module and adding `aead-stream` needs a
  download and a workspace `Cargo.toml` change. K4 §11's STREAM BE32 is built on `XChaCha20Poly1305` in one pure
  file: nonce = 19-byte prefix ‖ BE32 part counter ‖ last-flag byte (0 or 1); the counter never wraps (a
  recording that would need part 2^32 stops `size_limit` first, since 2^32 × 64 KiB far exceeds any limit, and
  the code refuses it anyway). Associated data of every part = the header bytes.
- **G-3 Free space through `rustix::fs::statvfs`** (safe API, `rustix` 1.1.6 is already in the lockfile;
  `unsafe_code` stays forbidden). The `crates/hub/Cargo.toml` line goes in the T4 Handoff commit.
- **G-4 Where the row is made.** `startSession` only checks that recording is possible (K4 §1 step 2: root
  set, writable, ≥ 1 GiB free) and sets `ticket.recording` and the audit `"recorded": true`. The recorder,
  started by the tunnel when the relay starts (after `ready`; for SSH at the first `resize`), makes the key,
  seals it, inserts the row (`expires_at` per G-6), then creates the file with `create_new` and mode 0600. A
  file that cannot be created sets `stopped_reason = write_failed` (the row exists, so `STOPPED` shows). A
  session that ends before its relay starts has no row: nothing was recorded.
- **G-5 `Session.recording`.** Read from the row: no row is `OFF`; a row with `stopped_reason` is `STOPPED`;
  otherwise `ON` (live or ended). A stop publishes `sessionChanged` and writes a Warning event with a fixed
  sentence per reason, never a path or byte count.
- **G-6 Expiry (CR-19, Q-1 accepted).** K3 gains `sessions -> retention` (`retention::periods` only). The recorder
  sets `expires_at = started_at + period` at insert; the daily job re-sets it from the current period, deletes
  expired rows, then their files, then orphan `.anrec` files. T4 writes the K3 text and the
  `quality/hub-modules.json` edge with the code.
- **G-7 Playback tickets** live in their own table under `recording/`, as `files::Tickets` does, with every
  K4 §1 property, bound to `/recording`. `Live` gains the field (one line in `live.rs`).
- **G-8 Delete order (D-13, K1).** `deleteRecording` deletes the row (which holds the only sealed key) and
  commits, then removes the file; a file left by a failed remove is unreadable and the retention job sweeps
  `.anrec` files with no row. An open playback of it ends `DAMAGED` or `MISSING`.

## Questions to the programme orchestrator

- **Q-1 Recording expiry needs a period at insert.** K2 stores `sessions.recordings.expires_at`, and K1 shows
  `Recording.expiresAt`, but `sessions` may not import `retention` (K3), so the recorder cannot read the
  current recordings period. Proposal: K3 gains the edge `sessions -> retention` (`retention::periods` only;
  `retention` imports nothing, so no cycle). The recorder sets `expires_at = started_at + period` at insert;
  `drop_expired_recordings(db, root, now, keep)` first sets `expires_at = started_at + keep` on rows that
  differ (so a changed period applies within a day), then deletes rows with `expires_at <= now`, then their
  files and any `.anrec` file with no row. Alternative without a K3 change: `Serving.recording` carries no
  period, the row stores `started_at + 30 days` (D-25 default) and the daily job corrects it, so
  `expiresAt` can be wrong for up to a day after a period change.
- **Q-2 Path for T1's proof test.** `apps/client/src/lib/sessions/recording/` is WP-49's. Proposal:
  `apps/client/src/lib/sessions/tunnel/vendor/session-recording.test.ts`, beside the vendor file it proves
  (no Phase 3 owner), reading the hub's guacd fixtures by relative path. Or WP-49's folder, as a handoff.
- **Q-3 Ordering with WP-47.** T7 (terminal tee) starts after WP-47 T5 merges, T8 (Guacamole tee) after WP-47
  T6 merges; T5a (`start.rs`) after WP-47 T2 merges. `WatchTicket.recording` (WP-47 S-16) is served by
  WP-47's resolver from the session's recording state; T5a gives the sessions-side read and a handoff note.
