## Decisions

- **D-1 Chart primitives in `lib/charts/`.** One pure geometry module (time and value scales, paths with gaps
  for missing points, the min–max band, ticks for the axes and the grid) and one line chart component. The
  checks tab's response-time chart moves onto it, so `lib/charts/` has two users and `checks/chart.ts` goes.
- **D-2 Chart update motion (5.7.3).** A new point comes in at the right edge. The drawn line starts offset by
  the distance the time axis moved and goes to rest on `spring-default`, from where it is on screen (MOT-002).
  Only `translate` animates (MOT-006). Reduced motion: instant. A range change replaces the chart with a
  cross-fade (`duration-base`). The motion runs once per new point; nothing repeats (MOT-011).
- **D-3 Loading (5.7.3, MOT-007).** A chart's skeleton is the chart box with its grid and axes and no line:
  the same geometry, no shimmer. It shows after `threshold-loading` through the existing `skeletonDelay`
  and is replaced with a cross-fade.
- **D-4 Charts per metric (MET-003, MET-009).** One chart per `MetricKind` group for the chosen range: CPU,
  memory (percent), each disk mount (percent), network in and out (one chart, two series), load (1, 5, 15),
  uptime is a fact, not a chart. Per GPU: a usage chart and, only for a GPU with its own memory, a VRAM
  chart (MET-007), each titled "GPU <index> <name>" (MET-009). Percent charts have a 0–100 axis and the
  85 % threshold line in `chart-threshold` (MET-004). Series colours come from `chart-series-1` … `-6`.
- **D-5 Ranges and live points.** The range control offers 1 hour, 24 hours and 7 days (MET-003; K1
  `HOUR`, `DAY`, `WEEK`), kept in the URL as `?range=` beside `tab` so Back and reload keep it. Only the
  1-hour range takes live points from `metricsAdded(deviceId)`; points older than the window drop off the
  left. The 24-hour and 7-day ranges are aggregates (WP-28 D-7) and reload on a range change.
- **D-6 State at the route.** The panels take data and callbacks (Phase 1 D-1). A `DeviceMetrics` state
  class in `overview/` owns the request, the subscription and stop; the route creates it and starts it
  the first time the Overview tab shows (Phase 1 D-9). That is a few lines in `+page.svelte`, outside the
  owned paths, named in each R-067 message.
- **D-7 Pending members.** The documents live in `lib/metrics/api.ts` (one GraphQL client per domain,
  CQ-045). Metrics are asked for only when `metricsSource` is `SSH` (a served field). With `NONE` the
  Overview shows "No metrics" and a link to Settings, and sends no request. Until WP-28 T4 serves K1, an
  SSH device shows the hub's error with Retry in the chart area; this is recorded as an open risk.
- **D-8 Shared metric bars.** WP-26's bars (`lib/devices/readings/`) have the final geometry and rules
  (MET-004, MET-007, MET-008, MOT-008). They move, without rewriting, to `lib/metrics/bars/`, typed by a
  structural readings type so `lib/devices` can use them without a cycle. The Overview shows the current
  readings with them above the charts, so the shared bar has two users. Handoff H-1 asks the `lib/devices`
  owner to import them and delete `lib/devices/readings/` (P2-WAVE-003).
- **D-9 Per-tab skeletons.** `TabPanel` takes an optional skeleton snippet; the Overview passes the chart
  grid skeleton, the others keep the list rows. No tab changes size when its data arrives (MOT-007).
- **D-10 Sessions tab.** The table gains a Protocol column (SSH, RDP, VNC; RA-030). `clientAddr` (RA-034)
  is `@pending` and its document belongs to `lib/sessions/api.ts` (WP-24), so it is a could, not built.
