## Decisions

- **D-1. State on the check row.** `checks.checks` gains these columns (K2 allows added columns):
  - `status`, `failures`, `next_due_at`, `last_beat_at`;
  - `cert_not_after`, `resolved_ip`, `push_token`, `secrets_sealed`.
  
  `statuses` and `device_status` then read one row per check instead of raw heartbeats (CHK-011).
- **D-2. Partitions.** `checks.heartbeats` is partitioned by UTC day, with no default partition. Two `SECURITY DEFINER` functions manage the partitions:
  - `checks.ensure_day_partition(instant)` creates a day partition;
  - `checks.drop_day_partitions_before(cutoff, instant)` drops old ones. It refuses a cutoff newer than 30 days before `least(instant, now())`.
  
  Both are owned by the owner role, run with `search_path = pg_catalog, pg_temp`, and have EXECUTE revoked from PUBLIC and granted to `anima_runtime` (R-016, R-023).
- **D-3. Aggregates.**
  - `uptime_minute`, `uptime_hour` and `uptime_day` are upserted in the same transaction as the heartbeat (DB-008).
  - The three tables have a foreign key to `checks.checks` with ON DELETE CASCADE.
  - Heartbeats have no foreign key. The retention job deletes heartbeats whose check is gone (R-004).
  - Aggregate rows are deleted by bucket age: 7 days, 90 days and 2 years (DB-009).
  - Heartbeat retention drops whole partitions (DB-005).
- **D-4. Uptime.**
  - The ratio is (up + degraded) / (up + degraded + down).
  - It is read from the coarsest table that covers the window: DAY reads minute rows, WEEK and MONTH read hour rows, YEAR reads day rows.
  - Maintenance and Unknown buckets are not counted. With no counted beats the result is null (CHK-011).
- **D-5. Status rules (CHK-004, CHK-006).**
  - A check's status is its stored state. It is Unknown before the first beat and while the check is paused.
  - A device's status is the `worst` of its checks that are not paused. A group check counts as the worst of its children.
  - A device with no checks is Unknown.
  - With the manual flag, or an active window that covers the device, the check or a tag, Down becomes Maintenance. The other statuses are kept.
- **D-6. Evaluation (CHK-002, CHK-008).**
  - Evaluation is pure: `evaluate(prev, probe, cfg, now) -> (state, status)`.
  - Invert is applied first.
  - A failure below `retries` keeps the previous status and schedules the next probe after the retry interval.
  - A success slower than `degraded_threshold_ms` is Degraded.
- **D-7. Scheduler.**
  - One task. Time comes from `Clock` and jitter from an injected RNG; only the first run of each check is spread over its interval.
  - At most N probes run at the same time.
  - Watchdog: one Error event for each lateness episode longer than 2 intervals (CHK-010).
  - Daily jobs: create partitions ahead, drop old partitions, trim aggregates, sweep orphan heartbeats.
- **D-8. Network limits (security).**
  - Probes go only to addresses the policy allows. The policy refuses loopback, unspecified, link-local (including 169.254.169.254) and multicast addresses.
  - Every resolved address and every redirect hop is checked. The probe connects to the address that was checked, so DNS rebinding cannot change it.
  - Response bodies are capped at 1 MiB.
  - Heartbeat messages are capped at 512 characters and stripped of control characters. They never contain header values.
  - No shell is ever started (CHK-012).
- **D-9. Secrets.**
  - HTTP basic passwords, bearer tokens, and the values of Authorization and Cookie headers are sealed (SEC-003) and never returned (K1). This waits for E-3.
  - GraphQL inputs that carry a secret get a hand-written parse that never echoes the value (WP-06 H-4).
