## Decisions

- **D-1. `Operator`, `ClientAddr` and `HeartbeatSummary` are defined in `events`.** K3 gives `events::NewAudit` an `Operator` and a `ClientAddr` field and `events::Signal::Heartbeat` a `HeartbeatSummary`, but `events` may import no domain, while `Operator`/`ClientAddr` are listed under `access` and `HeartbeatSummary` under `checks`. Every K3 path stays valid: `events` defines the three types, `access` re-exports `Operator` and `ClientAddr` (`pub use`), and `checks` (WP-09) uses `events::HeartbeatSummary`. No signature changes. Raised to the programme orchestrator for confirmation.
- **D-2. `AuditAction` and `AuditTarget` shape.** K3 names them without a definition. `AuditAction` is a closed enum of verbs (`Login`, `Logout`, `Create`, `Update`, `Delete`, `Start`, `End`, `Accept`, `Pause`, `Resume`, `Activate`, `Deactivate`); `AuditTarget` is an enum over the leaf ID types (`Operator(OperatorId)`, `Site(SiteId)`, `Device(DeviceId)`, `Check(CheckId)`, `Window(WindowId)`, `Session(SessionId)`, `Credential(DeviceId)`, `HostKey(DeviceId)`), which gives `target_type` and `target_id` text. Other packages add no variants without a handoff to WP-05.
- **D-3. Redaction in `audit` and `record`.** *Caller rule:* callers never put secret values in `change`, `message` or error text; redaction is defence in depth. Before it writes, `audit` replaces secrets in `change` with `"[redacted]"`, at any depth and inside arrays (K1 `AuditEntry.change`, LOG-007). `record` applies the *Values* rules below to `message` and to the device name before it stores and publishes them, so a device called `postgres://admin:pw@db` reaches neither the log nor the bus (T5 round 2, H-6). Booleans are never redacted. *Names.* A key is normalised with NFKD, combining marks dropped (`pässword` gives `password`), split into words at every character that is not an ASCII letter or digit and at case changes (`apiKey`, `api_key`, `APIKey` give `api`, `key`), lower-cased; a plural `s` on the last word is dropped (`apiKeys`), a double `ss` is not (`pass`). A name names a secret, tested first, when it contains `key` and `private` or `priv` (`privateHostKey`, `hostKeyPrivate`, `privNodeKey`), when the joined words contain `password`, `passwd`, `passphrase`, `passcode`, `secret`, `token`, `jwt`, `authorization`, `cookie`, `bearer`, `privatekey`, `privkey`, `authkey`, `keymaterial`, `totp`, `otpauth`, `recoverycode`, `backupcode` or `mfacode`; or when a whole word is `otp`, `pem`, `pin` (not when the name also contains `cert`, `tls` or `spki`), `pass`, `pwd`, `pw` or `psk` (not `auth`: `authType` names a method; `authKey`, `authToken`, `basicAuth`, `proxyAuth` and `authorization` match the parts, `basicauth` and `proxyauth` being parts too). A key named exactly `auth` is decided by its value: a method name (`password`, `key`, `publickey`, `private_key`, `none`, `token`, `totp`, `basic`, `agent`, `keyboard-interactive`, `kerberos`, both sides compared normalised) stays, an object or array under it is a credential holder, and any other scalar is redacted (`{"auth": "dXNlcjpodW50ZXIy"}`; T5 round 3). Otherwise a name ending in `hostkey`, `publickey`, `nodekey` or `authorizedkey` is kept (public keys, audit evidence for LOG-005, SEC-006, WEB-009), so `secretHostKey` and `passwordNodeKey` are secrets but `sshHostKey` is not. Otherwise the key names a secret when the last word is `key` or the joined form ends with `apikey`, `sshkey`, `accesskey`, `signingkey` or `encryptionkey`. A name containing `credential` or the word `cred` (`creds`, `sshCreds`), and not ending in the word `id`, holds credentials: a scalar under it is redacted, and inside an object or array under it, at any depth, every non-boolean scalar is redacted except an RFC 3339 timestamp and the scalars under the metadata names `kind`, `type`, `username`, `id`, `fingerprint`, `createdAt`, `updatedAt`, `rotatedAt`, `storedAt`, `expiresAt` and `lastUsedAt` (a closed list: `valueAt`, `oauthAT` and `at` are redacted); a secret name there is redacted whatever it holds, and an object under a metadata name stays under the holder rule (T5). `keyboard`, `monkey`, `keyId`, `credentialId`, `privateIp`, `auth`, `authType`, `signIn`, `notPaused`, `footprint` and `hotplug` are kept, and so is an enum value such as `"password"` under a plain key (`{"method": "password"}`). *Labels.* In an object whose `field`, `path`, `key`, `setting` or `property` value names a secret, or whose `name` names one when the object also has a `value` (a header), every sibling except the label and `op` is redacted, whole subtrees included. A path label names a secret if any `/` or `.` segment does (`/ssh/password`, `ssh.key.type`, `/password/value`, `/credentials/0/value`); an array index or `-` never does. `name` is not a label otherwise (a device may be called `secret-lab`). *Values* (in every audit string, event message and device name; `events/redaction/text.rs`). A string containing a PEM `-----BEGIN` … `PRIVATE KEY`, `PuTTY-User-Key-File-`, `otpauth://` or `authorization:` (case-insensitive) is replaced whole. Otherwise only the secret inside it is masked, so the rest of an operator's text stays (T5 round 3). Every pass takes time linear in the text's length: the JWT pass skips an `eyJ` inside a run already scanned, the URL pass reads only the authority and the word after it, and the key pass resumes after each masked value (T5 round 4, S1): (1) *URLs:* after `://` the authority ends at the first `/`, `?`, `#` or whitespace, and the userinfo at the last `@` inside it; with a `:` the part after the first `:` is masked (`user:[redacted]@host`, `john@example.com:[redacted]@ftp`), and without one the whole userinfo is masked only when it is credential-shaped (`https://[redacted]@github.com/…` for `ghp_…`), so plain usernames stay (`ssh://root@host`, `deploy-user@host`), a deliberate choice for operator text. When the authority has no `@` but a `:` that is not followed by a port (digits, after any `[…]` IPv6 literal), the password may hold an unencoded `/`, `?` or `#` (`https://u:pa/ss@h`): it is masked up to the next `@` in the same word. `https://a.example:443/x,https://b.example/@me`, `http://[::1]:8080/@me` and `rtsp://cam.local:554/stream@main` stay. (2) *`key=value` and `key: value`:* the key is the run of ASCII letters, digits, `_`, `-` and `.` before the separator, which is `=` or `:` with optional spaces or tabs before it and spaces, tabs or line breaks after it (pretty-printed JSON) and an optional quote before it (`password = x`, `'password' : 'x'`, `{"password":"x"}`); when the key names a secret by the *Names* rules (`password`, `PGPASSWORD`, `dbPassword`, `accessToken`, `api_key`, `client_secret`, `id_token`, `spring.datasource.password`, `pin`), the value is masked: the inside of a quoted value, or an unquoted value up to whitespace, `&`, `;`, `,`, `}` or a quote (libpq, JDBC, ADO, query-string and embedded-JSON forms). An empty value, `true`, `false` (any case), and an object or array (`{`, `[`) stay, so `passwordless=true`, `hasPassword=False`, `cwd=` and `OLDPWD=` stay (T5 round 4, S2). (3) *Schemes* (run before the key pass, so `authorization=Basic …` and `token=Bearer …` mask the credential and not only the scheme word; T5 round 4, N1): `Bearer`, `Basic` or `token` at the start of a word, then whitespace or `:`, then a credential-shaped token: the token alone is masked (`Bearer [redacted]`, `token: [redacted]`). *Credential-shaped* means 8 or more base64, base64url or JWT characters (`A–Z a–z 0–9 + / = - _ .`) with a digit, one of `+/=_`, or a capital after the first character; so `Basic tier`, `Basic connectivity check passed`, `Bearer Required` and `token expired` stay. (4) *JWT:* anywhere, `eyJ` at the start of a word followed by two `.`-separated segments, the payload not empty and the signature possibly empty (unsigned); a full stop right after it stays. *Accepted over-matches:* the value after any `:` whose preceding word names a secret, as in prose (`secret-lab: down`, `token: Expired`) and `pwd=/home/op` (`pwd` is a password word in libpq and JDBC); every non-metadata scalar inside a credential holder (`{"credential": {"deviceId": …}}`), any name with `priv` and `key` (`privilegeKey`); strings under names like `tokenExpiresAt`, `passwordChangedAt` or `passThreshold`; a credential-shaped URL user (`user1234@host`); a scheme word followed by a camel-case or digit-bearing word (`Bearer PowerShell`, `token v2.1.0-beta1`); a URL whose authority has a non-port `:` and an `@` later in the same word; the value of a plain `{"key": …}` that is not a label; every sibling under a secret label; data-looking path segments (`/passwordPolicy/minLength`). *Accepted leaks:* object keys are never redacted (a secret used as a key name stays, C5); whitespace inside an unencoded URL password or an unquoted `key=value` value (only the part before the space is masked); a credential of fewer than 8 characters, or of only lower-case letters, after a scheme word; a scheme word inside a longer word (`mytoken: …`); tuple-form diffs (`["password", "old", "new"]`) and label names not in the list (`fieldName`, `attribute`, array-shaped paths); secrets in other scripts or homoglyphs; secrets in free text without one of the value markers. T5 round 4 also accepts: JWTs behind `%20` or `\n` escapes (the `eyJ` does not start a word), JWTs with trailing dots, the five-part JWE form and headers that are not compact JSON (S3); a non-ASCII gap after a scheme word (`Bearer` and a no-break space), a scheme credential cut by a `%` escape (`Bearer abc%2Bdef12345` stays, its first part being too short), and a credential that is not credential-shaped after a scheme word without a `:` (`token Pa$$w0rd123`; with a `:` the key rule masks it, and `bearer=…` is masked by the key rule too) (C1); an unterminated quoted value (masked only up to the first terminator), an escaped quote inside a quoted value (`"a\"b"` keeps `b`), and ODBC `{…}` values (`Pwd={a;b}`) (C2); `auth` reached through a JSON-patch or field label is not decided by its value (`{"path": "/ssh/auth", "value": "dXNl…"}` stays, `auth` not being a secret name) (C3); acronym plurals (`PSKs`, `PINs`) do not normalise to a secret word (C4). Partition dates are not bounded in the future (a bound would break fixture-date tests; T2's job owns creation), nor are BC dates refused.
- **D-4. Partitions and retention.** `event_log` and `audit_log` are partitioned by UTC day (DB-004) with no default partition. Two SECURITY DEFINER functions in `events`, owned by the owner role, with `search_path = pg_catalog, pg_temp` and every name schema-qualified, are the only way to create or drop a partition (the runtime role does not own the parents; K2 "Roles", R-016). `events.ensure_day_partition(parent, instant)` creates the day's partition if it is missing and revokes UPDATE, DELETE and TRUNCATE on it from `anima_runtime`. `record` and `audit` call it before the insert as a fallback, so an insert never fails for a missing partition (also in other domains' `#[sqlx::test]`s at fixture dates); `events::create_partitions_ahead(db, today, days)` creates them ahead in short transactions, because the fallback holds an ACCESS EXCLUSIVE lock until the caller commits. `events.drop_day_partitions_before(parent, cutoff, instant)` drops the partitions of days before `cutoff` and refuses a `cutoff` inside retention (90 days for `event_log`, 1 year for `audit_log`) of `instant` or of the database clock, whichever is earlier, so a caller cannot claim a later "now" (LOG-006). `events::drop_expired_partitions(db, now)` asks for one day less than allowed, so a hub clock slightly ahead of the database is never refused. T2 schedules both at start and daily. Future partitions are not bounded (a bound would break fixture-date tests).
- **D-5. Bus publish timing.** `record` publishes `Signal::Event` after its insert, inside the caller's transaction. A rolled-back transaction can leave a published event that is not stored. Accepted for Phase 1 (the subscription is a live view; the list query is the truth); documented on `record`.
- **D-6. Operator in the request.** An async-graphql guard cannot add data to the context. The HTTP and WebSocket edges resolve the bearer token once per request (`access::operator_for_token`) and put the `Operator` in the request data; `Authenticated` checks that it is there and returns `UNAUTHENTICATED` otherwise. Resolvers read `ctx.data::<Operator>()`. An access schema extension refuses any operation without an operator unless every root field is `login` (API-003 backstop for a resolver that forgets the guard).
- **D-7. Tokens.** 32 random bytes, base64url, shown once; the database keeps SHA-256 of the token (high entropy, so a fast hash is enough). Login tokens have scope `write` and expire after 30 days; `logout` deletes the token. `last_used_at` is updated at most once a minute.
- **D-8. Login throttle (revised after T3 security review).** Each attempt is written to `access.login_attempts`. Five failed attempts for one (username, client address) pair, or from one client address for any username, in 15 minutes refuse further attempts from that address for 15 minutes, with the same error as a wrong password. There is no username-wide lock: with one operator account (OD-2), a username-wide lock let any VPN device keep the operator locked out with 5 requests every 15 minutes. Guessing from many addresses is bounded by the small, enrolled VPN (VPN-004). `operator set` clears the username's attempts, so there is a documented way back in. An unknown username still runs one argon2id verification (against a fixed dummy hash) so timing does not reveal it; a throttled attempt skips it (accepted: same message and code, less CPU under a flood).
- **D-9. Operator bootstrap (revised after T3 security review).** The spec has one operator account (OD-2) and no sign-up. `anima-hub operator set <username>` reads the password from standard input (no echo on a terminal) and, in one transaction, creates the single operator or replaces the existing one: username and argon2id hash, all its tokens deleted, its login attempts cleared. A second account is never created. `anima-hub operator totp <username>` enrols TOTP and prints the `otpauth://` URI once, only when standard output is a terminal: into a pipe or file it refuses before changing anything, so the secret never lands in a log or file. Enrolling replaces any earlier secret and, in the same transaction, deletes all the operator's tokens, so every client signs in again with the second factor. `anima-hub operator totp <username> --disable` removes the secret (`--disable` alone is a usage error, since it is a valid username). A TOTP code is accepted only for a step later than the last one used (RFC 6238 5.2), which costs this: a code for the next step (clock drift ahead) blocks the current step's code until the next step passes. A sign-in issues its token in one transaction that locks the operator row, checks that the username, password hash and TOTP secret are still the ones checked, and claims the TOTP step, so an `operator set` or `operator totp` that commits during the password check leaves no token (T6 security review). A TOTP secret that does not open with the hub key answers like a wrong password, counts toward the throttle, logs the `totp_secret` fault and records an `ACCESS` event at `error` severity, the highest K3 has. Logic is in `access`; `main.rs` only dispatches (handoff).
- **D-10. Permitted networks.** The effective list is the rows of `access.permitted_networks`. At start `main.rs` calls `access::permit_networks(&db, &config.permitted_networks)` to upsert the `ANIMA_PERMITTED_NETWORKS` entries (label `ANIMA_PERMITTED_NETWORKS`). The layer caches the list for 30 seconds (clock passed in). Site subnets are not added automatically: `access` may not read `devices.sites` (K2, K3). The operator lists them in `ANIMA_PERMITTED_NETWORKS`. Open question for the programme orchestrator.
- **D-11. Client address.** The client address is the TCP peer (`ConnectInfo<SocketAddr>`); the hub is reached directly over the VPN, so `X-Forwarded-For` is never trusted. An IPv4-mapped IPv6 peer is normalised to IPv4. Refusals are written to the event log (source `ACCESS`, severity `WARNING`) at most once a minute per address, so a scan cannot flood the log.
- **D-12. Layer return type.** K3 writes `-> impl tower::Layer<Route> + Clone`. A bare `impl Layer` hides the service type, which `Router::layer` needs, so the function returns `impl Layer<Route, Service: …> + Clone` with the associated-type bounds spelled out (or a named layer type). Callers write the same `.layer(access::permitted_networks_layer(db, bus, clock))`.
- **D-13. Bind and TLS.** At start the hub refuses a listen address that is unspecified (`0.0.0.0`, `::`) or public (NET-003, SEC-008), and serves TLS with rustls from `ANIMA_TLS_CERT_FILE`/`ANIMA_TLS_KEY_FILE` (SEC-001). Plain HTTP only when both TLS variables are unset and the listen address is loopback (tests and local development). Private addresses are accepted (R-021 H-1b): loopback, RFC 1918 (`10/8`, `172.16/12`, `192.168/16`, as compose binds `172.30.0.10:8443` and publishes only on the VPN address), the VPN range `100.64/10` and IPv6 ULA `fc00::/7`; everything else that is routable is refused. The certificate reloads without restart when its files change (R-021 H-2, DNS-002): an hourly mtime check of both files swaps the rustls config; a reload that fails keeps the old certificate and logs the fault kind, never key bytes.
- **D-14. Test database.** Superseded by R-009: `bun run gates` runs `cargo test` against a throwaway PostgreSQL 17 (`quality/bin/with-postgres.ts`). Database tests never skip without a database (CQ-024) and never create tables in another domain's schema (CQ-032). Builders use the package's scratch server (`127.0.0.1:55432`) by exporting `DATABASE_URL`, which `with-postgres` respects. *One server per concurrent suite:* `#[sqlx::test]` (sqlx 0.8 and 0.9) names each test database after the test path only and drops it with `drop database if exists` before creating it, so two processes running the same test paths on one server (two worktrees that both contain T1, or a builder and a reviewer) destroy each other's databases (`23505` on `pg_database_datname_index`, `3D000`). Different suites on one server do not collide. Concurrent runs of the same suite therefore each need their own server: unset `DATABASE_URL` so `with-postgres` starts one, or use a server per worktree.
- **D-15. Out of hub scope.** NET-004 ("Not on the network" in the navigation bar) is client work (WP-11); SEC-009 (client never logs tokens) is client work (WP-11, WP-16). The hub side of both: GraphQL errors and the process log never contain tokens (LOG-007), tested here.
- **D-16. Roles (R-016).** One runtime group, `anima_runtime` (NOLOGIN), created by migration `0001_access_runtime_role.sql` (0001 is T1's; T3 starts at 0002). The same migration runs `ALTER DEFAULT PRIVILEGES` for the owner role (USAGE on schemas; SELECT, INSERT, UPDATE, DELETE on tables; USAGE, SELECT on sequences; EXECUTE on functions), so every later migration's objects reach the runtime role. Migration 0500 makes the explicit exception: UPDATE, DELETE and TRUNCATE are revoked on both log parents and on every new partition. The DO block refuses an existing `anima_runtime` with more rights than a plain NOLOGIN group, and migration `0501_events_runtime_group_check.sql` checks again after the grants, because 0001 swallows `duplicate_object` when another database's migration creates the group in between (T5). One cluster serves one Anima installation, since the group is cluster-wide (R-019, DB-001; recorded in 0501's header). 0500's explicit EXECUTE grants on its partition functions deliberately duplicate 0001's default (0501's header). `events::check_runtime_role(db)` is the start check (T5, K2 "Start check" as rewritten by R-023). It counts every role the login, `session_user`, is a member of (`pg_has_role … 'MEMBER'`, so `SET ROLE`, grants without INHERIT and ADMIN OPTION count) and refuses, with a plain error (API-010) and in this order: a missing `events.audit_log` (not migrated); a superuser; a session that runs as another role (`session_user` differs from `current_user`, set by `ALTER ROLE … SET role` or `options=-c role=…`, which would hide the login's own rights until `RESET ROLE`); an owner of the database, schema `events` (who may drop its tables) or `events.event_log`, `events.audit_log` or any partition below them (`pg_inherits`); a member of `pg_execute_server_program`, `pg_write_server_files`, `pg_read_server_files` or `pg_maintain`; a holder of UPDATE or REFERENCES on any column, or DELETE, TRUNCATE, TRIGGER or MAINTAIN, on a log table or partition (directly, through `pg_write_all_data` or PUBLIC), or of CREATE on `events`; and a `pg_default_acl` entry for tables, global or in `events`, that grants UPDATE, DELETE, TRUNCATE, TRIGGER, REFERENCES or MAINTAIN to PUBLIC or to a role in the login's set other than `anima_runtime`. `anima_runtime`'s own write defaults are 0001's, for every other domain's tables; they never reach a partition, because migration `0502_events_partition_privileges.sql` replaces `events.ensure_day_partition` (same signature, SECURITY DEFINER and `search_path`) so a new partition loses every grant except the owner's, PUBLIC included, and then gets exactly SELECT and INSERT for `anima_runtime`. `pg_read_all_data`, `pg_monitor` and `pg_signal_backend` stay allowed. The check reads only the catalog and the privilege functions by OID, so it needs no USAGE on `events`. The store returns the first refusal as `events::Refusal`; `check_runtime_role` returns `events::RoleError` (`Database` or `Refused(Refusal)`), separate from `events::Error` (which `record` and `audit` keep, one variant). `RoleError` is returned only at start, before serving, so it never reaches GraphQL. 0001 and 0501 refuse an `anima_runtime` that is a member of any role, the four predefined roles included. The hub's database URL sets no `options=-c role=…` (WP-04). T3 calls the check from `main.rs` after the `migrate` subcommand. Restriction tests run as the throwaway superuser with `SET ROLE anima_runtime`; start-check tests log in as real LOGIN roles (the throwaway server trusts local connections).
