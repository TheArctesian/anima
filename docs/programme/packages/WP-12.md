## Decisions

- **D-1 Domain clients (CQ-045).** There are three clients, each a function of a `Hub`:
  - `devicesApi(hub)` in `$lib/devices/api.ts`: the `devices` list, `tags` and `deviceStatusChanged`.
  - `checksApi(hub)` in `$lib/checks/api.ts`: `heartbeatAdded`.
  - `eventsApi(hub)` in `$lib/events/api.ts`: `events` and `eventAdded`.

  Documents live only in these files. `bun run --cwd apps/client graphql` regenerates the types. Results stay `HubResult` values. Components show the K7 error text and never throw.
- **D-2 Pure state, thin components.** Each domain has a pure state module (`list.ts`, `heartbeats.ts`, `log.ts`) with functions `(state, input) → state`. Components hold a `$state` of it and call the API. Time is a parameter (`now`), never read inside the core.
- **D-3 Server filter and sort, client live order (DEV-002–004).**
  - Filter and sort go to the hub as `DeviceFilter` and `DeviceSort`.
  - A live status change updates the device in place.
  - When the list is sorted or filtered by status, the client applies the same order and filter. The row then moves or leaves without a reload (Reorder role). The client order is the one in E-1.
- **D-4 Page state in the URL.**
  - View (grid or table), name text, status set, tags and sort are URL search parameters (`view`, `q`, `status`, `tag`, `sort`). Pure functions parse and write them.
  - Back and Forward restore the list.
  - Unknown values are dropped, not errors.
  - The name filter sends its request 200 ms after the last keystroke. This delay is not an animation timer, so MOT-042 does not apply.
- **D-5 First page size (DEV-001).** The page requests `first: 200`, the K1 maximum (API-006). It shows a "Load more" button when `hasNextPage`. One request carries every card field, including the 24 h uptime and the heartbeats for the bar, so 200 devices render from one answer. The page stays at 200 after R-044: DEV-001 asks for 200 devices on one screen, and at one or two checks per device the answer holds 10,000–20,000 heartbeats of three fields each. WP-17 measures it.
- **D-6 Heartbeat bar (Section 6.1).** The bar shows the device's last 50 heartbeats. K1 has heartbeats only per check. So the client asks `checks { id heartbeats(first: 50) }`, merges them by `at` with the newest last, and keeps the last 50. `heartbeatAdded(deviceId: null)` adds new beats for every visible device. See E-2.
- **D-7 Card content.**
  - The card shows: the name, the host, the status pill, the 24 h uptime (`uptime(window: DAY)`; null shows "—") and the heartbeat bar. When the host is a name and `ip` is known, it shows the IP address too.
  - An "SSH" button shows when `ssh.enabled`.
  - No metrics row: K1 has no metrics in Phase 1, and Section 6.1 shows metrics only "if metrics are available".
  - No RDP button (Phase 2).
  - The card name links to `/devices/{id}`, which is WP-13's route.
- **D-8 Actions owned elsewhere.** "Add device" (in the DEV-005 empty state and the toolbar) and the card's "SSH" button are real buttons. Their actions are props of the page component: `onAddDevice()` and `onConnect(deviceId)`. WP-13's form and WP-14's session tab don't exist yet. Until they do, the route passes these handlers:
  - `onAddDevice()` navigates to `/devices/new` (H-1).
  - `onConnect(deviceId)` does nothing (H-2).
- **D-9 Logs panel (LOG-009, LOG-010).** A panel at the bottom of the Devices page with the `panel` material.
  - Filters: time (`since`: 1 h, 24 h, 7 d, all), severity, source and device. Each filter change reloads `events(filter, first: 100)`.
  - `eventAdded(minSeverity)` streams new rows. The subscription has no source or device argument, so the client keeps only rows that match the current filter.
  - The list is capped at 500 rows.
  - "Load older" pages with `after`.
  - Messages are shown as text, never as HTML.
- **D-10 Logs panel resize (Section 5.7.4, MOT-030–034).**
  - The panel edge follows the pointer 1:1 with `setPointerCapture`.
  - On release, `nearestSnap` picks a snap from the projected position: collapsed, 33 % or 66 % of the page height. The panel moves there with `spring-snappy` and the release velocity.
  - The keyboard reaches the same three positions: the edge is a `separator` with `aria-valuenow`.
  - The drag attachment lives in `$lib/motion/drag/`, following WP-11 H-7's subfolder rule (H-3).
- **D-11 Motion (Section 5.7.3).** Every motion uses the `$lib/motion/` helpers and `motionPreference()`, and each has its reduced-motion form from the roles table.

  | Role | Motion |
  | --- | --- |
  | Press | Buttons and cards |
  | Hover | Colour change, `duration-fast` |
  | Reorder | `measure`/`flip` with `spring-move`; new items `listRow` with `stagger-list` |
  | Status change | Pill cross-fade, `duration-base`; card-edge highlight over `duration-highlight` |
  | New heartbeat | Bar moves one cell left, `spring-default` |
  | New log row | FLIP, plus a highlight |
  | Menus | `popover` |
  | Loading | Skeleton only after `threshold-loading`, held at least `threshold-loading-min`; cross-fade to data |
- **D-12 Heading height (WP-11 H-7).** The page heading has a fixed `block-size` from tokens, so the font change cannot move the page.
- **D-13 Test hub.** Tests use one fake `Hub` (`$lib/devices/hub.fixture.ts`). It answers documents by operation name and lets a test push subscription values. WP-09's checks schema is not on `phase-1` yet, so status, uptime, checks and heartbeats come from this fake, shaped by K1.
