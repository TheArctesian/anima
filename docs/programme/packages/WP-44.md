# WP-44 — Client web build

Package branch: `claude/wp-44-web-client` from the local `phase-3` at 784355b1. Worktree: `.claude/worktrees/wp-44`.
Task branches: `wp/44-web/<task>`, each in its own worktree `.claude/worktrees/wp-44-<task>`.

Goal: the client built from the same code (CLI-001) runs in a browser served by the hub at its own origin. It signs
in with the `HttpOnly` cookie, never holds a token in script, leaves out the desktop-only features, opens web
interfaces in a new browser tab, runs under the K7 Content-Security-Policy, and is tested in Chromium, WebKit and
Firefox.

Spec: CLI-001, CLI-002, CLI-003, SEC-002, API-003, WEB-011, UPD-001, LOG-007, LOG-008, RA-002 (D-5 note), MV-001.
Plan: phase-3-plan.md WP-44 row, P3-WAVE-002/003, criteria 1–4 and 23, D-2 to D-6. Rulings: R-066 (two review
rounds, mutation runs only on security work), R-067 (send each accepted task), R-068 (client-only gates 4–12),
R-082/R-083 (handoff commits), R-081.

Contracts used (frozen for Phase 3, read only): K1 `signInBrowser(input: LoginInput!): BrowserSignIn!` (`@pending`
until WP-43 T2 merges), `logout`, `me`; K7 browser transport (cookie used only with no `Authorization` header and
`Origin` = public origin; an empty `connection_init` payload on a cookie socket), HTTP surface, static file headers
and CSP. Hub side is WP-43 (in review); this package builds against fakes made from K1/K7 (CON-003) and rebases when
WP-43 merges. WP-43 decisions that this package relies on: A-2 (the hub hashes each inline `<script>` of
`index.html` into `script-src`), A-3 (a browser token is accepted only from the cookie), A-4 (`signInBrowser`
without the same-origin mark is FORBIDDEN), A-8 (`logout` clears the cookie).

## Decisions

- **E-1 Base.** The package branch starts at the local `phase-3` head 784355b1, one commit after the 7a040156 named
  in the brief (a client CSS fix for selects on Linux, also local). Starting older would only add a rebase.
- **E-2 Served origin.** In a browser the hub address is the origin that served the page (CLI-002: no hub address
  field; the web client talks only to the hub that served it). `lib/platform/browser.ts` gives that address
  (`wss:` for `https:`, `ws:` for a loopback `http:` origin used in local tests). The desktop keeps its stored
  address. The token provider answers `null` in a browser: the cookie travels by itself and no token is ever in
  script (CLI-003, D-3).
- **E-3 Signed-out routes.** `/sign-in` and `/shared` (and below `/shared/`, exact segment match) need no sign-in.
  In a browser, the start guard asks the hub `me` on any other route and goes to sign-in on UNAUTHENTICATED (the
  cookie is `HttpOnly`, so script cannot look). `/shared` is a bare route for WP-49: the root layout renders only the
  page there — no operator hub, socket, nav, session strip, update banner or guard — so a share viewer calls no
  operator operation (SEC-002, D-7). WP-49 brings its own signed-out transport for `joinShare`.
- **E-4 Browser sign-in and sign-out.** The sign-in page uses `signInBrowser` in a browser and `login` on desktop.
  No token reaches script. After a good browser sign-in the client does a full load of `/devices`, so the socket
  reconnects with the cookie; after sign-out (`logout`, which clears the cookie) it does a full load of `/sign-in`,
  so no cookie-signed socket survives in the page. The hub address form shows on desktop only (CLI-002).
- **E-5 Web interfaces in a browser (WEB-011, D-5).** With no web view tabs, the Web button opens the interface in
  a new browser tab straight to the device: `window.open(url, '_blank', 'noopener,noreferrer')`, called
  synchronously in the click (no `await` first, so the popup blocker sees the gesture), only for `http:` and
  `https:` URLs. The pinned SHA-256 fingerprint shows inside the Web menu, under the choice it belongs to (E-11,
  R-087), so the operator can compare it with the browser's certificate view; the browser cannot pin (WEB-008
  stays desktop).
- **E-6 CSP.** WP-43 A-2 hashes the inline scripts of `index.html` at hub start. WP-44 keeps the build clean for
  the K7 policy: only SvelteKit's own inline start script, no `eval`/`new Function`, no inline event handler, no
  worker or frame from `blob:`. A browser test runs the production build under the exact K7 header, with hashes
  computed as A-2 does, and fails on any `securitypolicyviolation`.
- **E-7 Browser tests.** Playwright (exact version pin) in `apps/client/browser/`, with three projects (Chromium,
  WebKit, Firefox). A synthetic hub answers inside Playwright at `https://hub.anima.ing`: `context.route` serves the
  production build with the K7 headers and answers `POST /graphql` by running the K1 schema with `graphql-js` over
  the contract fixtures; `routeWebSocket` answers graphql-ws and the session tunnels. No real hub, no secret; every
  other request is aborted. Not a gate: gate 7 (test) runs before gate 8 (build), and a new gate is a programme
  change. Script: `bun run --cwd apps/client test:browsers`. Builders of web behaviour and their reviewers run it;
  WP-53 uses it for acceptance.
  Ruling S3 (after T2) adds a deny-all proxy per engine, so a browser's own preconnects cannot leave the machine,
  and a global teardown that fails the run on any unexplained attempt; T6 built it.
- **E-8 Handoff files.** See Constraints. The programme orchestrator reads each handoff commit at merge.
- **E-9 Review.** Two rounds per task (R-066); only must findings block. Security tasks (T1, T2, T4, T5) get
  reviewer-security (Opus) with a scoped mutation run (20 minutes); UI tasks (T2, T4, T6) get reviewer-interface,
  which measures only this package's screens, once (WebKit and Chromium, MV-001).

- **E-10 T1 shoulds carried into T4.** T1 is accepted at round 2 with two shoulds that T4 (same folder,
  builder-heavy, reviewer-security) takes instead of a third T1 round: S1 add `/%73hared` to the bare-start test
  table (kills the `startAt` raw-path mutant, which in Chromium reloads forever and opens the operator socket on a
  share URL); S2 state in the `BARE_ROUTES` doc that a bare route's `load` stays pure, because a crossing
  navigation runs the target's `load` in the old document before the reload (handoff to WP-49: no `joinShare` or
  token work in `/shared` `load`).
- **E-11 T2 pin placement (granted, R-087).** Round 2's interface review found the pin beside the button
  overflows the card footer, the table row and the detail header. Proposed: in a browser, when any interface has
  a pin, the Web button always opens the menu and each choice shows its own pin inside the panel
  (`white-space: normal`, `aria-describedby` from the choice to its pin). This reads criterion 3's "beside the
  button" as "next to the choice that opens the device". Needs a third T2 round, beyond R-066.
