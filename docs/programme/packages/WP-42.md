## Decisions

- **D-1 Tauri bridges stay in `lib/desktop/`.** CQ1-11 proposed moving each bridge beside its domain, but
  CLI-003 and its lint (`eslint.config.js`, "the Tauri API is imported only in `lib/desktop/`") forbid
  `@tauri-apps` elsewhere. `lib/desktop/` therefore keeps every `invoke` edge, renamed to kebab-case
  (`this-machine.ts`, `process-log.ts`, `system-settings.ts`). Components that are not bridges leave it:
  `RemoteLoginButton.svelte` goes to the device form beside the SSH section that shows it.
- **D-2 The web view bridge splits.** `lib/desktop/webView/` holds a Tauri adapter (`desktopWebView`,
  `pinning`) and pure parts (event parsing, fingerprint, the `WebViewShell` port, `codeOf`,
  `certificateFrom`). The pure parts move to `lib/web-interfaces/shell/`; the adapter stays in
  `lib/desktop/web-view/web-view.ts` (D-1; a sub-folder, because `lib/desktop/` is at the 12-file limit). `lib/sessions/web/` moves to `lib/web-interfaces/tab/`, and its `open/` to
  `lib/web-interfaces/open/` (WP-44 then owns `open/` for WEB-011).
- **D-3 Domain forms.** `lib/forms/check/` moves to `lib/checks/form/`. `lib/forms/device/` moves
  to `lib/devices/form/`; `AddDeviceModal`, `MachineChoice`, `add-device.ts` and `this-machine.ts` move to
  `lib/devices/add/` (amended at T4: `lib/devices/form/` would pass the 12-file limit, and "add" names the flow).
  `animations.fixture.ts` stays in `lib/forms/`: modal, device form, session and check-route tests share it. `lib/forms/` keeps `FormButton`, `modal/` and `disclosure/`
  (spec Section 13: form primitives).
- **D-4 Platform seam shape.** `lib/platform/` answers seven yes/no questions (`keyStore`, `webViewTabs`,
  `popOut`, `updates`, `processLog`, `thisMachine`, `systemSettings`). The desktop answers come from one
  function in `lib/desktop/` (the only `isTauri()` read for availability); `lib/platform/browser.ts` answers
  "no" to all seven (WP-44 then owns that file). `popOut` is "no" on desktop too today: the shell has no
  pop-out window command and the root layout passes no `PopOutPort` (WP-14 H-2), so "yes" would be untrue
  (Section 12, Predictable). The updater module is reached only by a dynamic import behind `updates`
  (UPD-001).
- **D-5 Hub import face.** `lib/hub/hub.ts` is the one face (CQ1-17's first option, the larger importer
  count). The lint restriction that keeps it is a handoff for `eslint.config.js`.
- **D-6 Casing rule.** The rule belongs in `quality/src/names.ts` (shared, plan says handoff). WP-42 renames
  every camelCase client `.ts` file so the rule passes on arrival, and hands the rule text to the programme
  orchestrator.
- **D-7 Review.** Two rounds per task (R-066); only must findings block. Opus reviews the platform seam.
  reviewer-interface measures the platform task, since it decides which controls show. No security tag: the
  key store and updater keep their code; the seam only chooses whether to call them. The Q2-15 allow-list
  change is checked by the reviewer for an unchanged accept/refuse set (existing tests).
