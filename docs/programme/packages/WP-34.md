Package branch: `claude/wp-34-acceptance` from `phase-2` at 551ee1da. Worktree: `.claude/worktrees/wp-34`.
Task branches: `wp/34-acceptance/<task>`, each in its own worktree `.claude/worktrees/wp-34-<task>`.

Spec: phase-2-plan.md Section 5 (the 18 Phase 2 acceptance criteria), spec Section 5.8 (MV-001 to MV-008),
CQ-050. Owned paths: `docs/research/`, `docs/programme/phase-2-acceptance.md`, acceptance tests, and any path a
fix task names (programme brief). Contracts used: K1 (no `@pending`, P2-002), K5 (token gate), K6 (synthetic

Gates: a client-only task runs gates 4–12 from its worktree (R-068): `bun install --frozen-lockfile`,
`bun run lint`, `bun run check`, `bun run test`, `bun run --cwd apps/client build`, `bun run quality:limits`,

or contracts change runs all 12: `env -u DATABASE_URL BASE_REF=a6c57db bun run gates`. One cargo command at a
time.

## Constraints

- No change to the VPS, Headscale, Cloudflare or GitHub. The live hub is not used. A live check is written as
  exact steps for the operator.
- No secret file is read. No credential goes into a log, a test name or this file.
- Never edit `crates/hub/src/schema.rs` or `main.rs` (PKG-001); ask the programme orchestrator.
- `quality/baseline.json` stays `{}`.

## Decisions

- **D-1 Paths of closed packages.** All of WP-20 to WP-33 are done. A fix task names every file it changes,
  and only those files change (programme brief).
- **D-2 Audits are tasks.** The motion audit (MV-001 to MV-008), the log audit (criterion 16) and the
  code-quality audit (CQ-050) are run by reviewers that built none of the code. Findings that fail the spec
  become fix tasks.
- **D-3 CQ-050 applies nothing.** CQ-050 says to apply only the items the operator accepts. The audit report
  goes to `docs/research/code-quality/phase-2.md`; no item is applied here. An item that is also a motion or
  acceptance finding is fixed under that criterion instead.
- **D-4 Live checks.** Agents cannot drive the operator's machines, the desktop app on real devices or the
  VPS. A criterion that needs them has status `operator`, with the exact steps in the acceptance matrix.
- **D-5 Motion rulings from the start (R-066).** WP-17 D-13 and D-14 apply: one audit and one re-measure.
  A new jump that a WP-34 fix did not cause goes to issue #1 as a could, unless it is a step of at least
  100 px under normal motion. Under reduced motion an instant change in place is the specified form and is
  not a finding.
- **D-6 Review cap (R-066).** At most two review rounds per task. Only must findings block.
- **D-7 GPU gap (R-073).** GPU discovery and GPU metrics (MET-006 to MET-010) are not built. Criteria 11, 12
  and 13 are judged on what exists, and the gap is named in the report, not built here.
- **D-8 Status words.** The matrix uses `pass` (evidence in the repository), `fail` (a spec failure that is
  open), and `operator` (the repository part passes; a live step only the operator can do remains).

  secret-shaped values; run the existing redaction tests with a mutation that removes one redaction.
