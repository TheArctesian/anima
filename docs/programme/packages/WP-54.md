## Decisions (D-n are proposals until the programme orchestrator rules)

- **D-1 Agent tokens live in `metrics`, not in `access.api_tokens`.** Tables `metrics.agents` (device_id pk fk
  cascade, token_hash, expires_at, next_hash null, next_expires_at null, enrolled_at, last_push_at) and
  `metrics.enrolments` (code_hash pk, device_id fk cascade, expires_at, used_at null). Reasons: an agent token
  is bound to a device, and `access` (range 0001–0099) may not hold a foreign key into `devices` (0100), so a
  deleted device would keep a live token; an agent token never in `api_tokens` cannot pass `operator_for_token`
  by construction (MET-013). The `metrics -> access` edge (CR-8) is then used for the shared bearer primitives
  (random bytes, canonical base64url, SHA-256, the no-`Debug` secret type) and for `Authenticated` on the two
  mutations; access also refuses any bearer with the `anima_agent_` or `anima_enrol_` prefix before a lookup.
  This differs from WP-43's note ("a fourth kind in `TokenKind`"). Needs a ruling.
- **D-2 Migration range.** WP-54 takes 0710–0729 (WP-46 has 0702; WP-51 may need 07xx for GPUs). The devices
  check change rides in the metrics range, as 0701 changed the events check. Needs a K2 line.
- **D-3 Rates move to `agent-core`.** The agent must turn 2 s readings into shares and rates exactly as the
  hub does, so `metrics/rates.rs`, the selection rules and `MAX_LABELS` in `metrics/series.rs`, and the plain
  `Sample` (without the GraphQL enum) move to `agent-core::points`, as WP-51 T1 moved the parsers. `MetricKind`
  keeps its GraphQL derive in the hub and converts from `points::Kind`. These files are WP-51's T1 paths;
  WP-51 T2/T3 may touch `series.rs`. Needs a ruling on who moves them and when.
- **D-4 Apple GPU through `ioreg`, no `unsafe`.** The agent runs `ioreg -r -d 1 -c IOAccelerator` each sample
  and uses WP-51 T2's pure reader. It reads the same IOKit `PerformanceStatistics` as the IOKit API, with no
  `unsafe` (the workspace forbids it; R-069 is the only exception). IOReport GPU power needs private API and
  `unsafe`, so it goes to issue #1 as a could ("where macOS gives it"). T5 then needs Sonnet, not Opus.
- **D-5 Agent distribution.** The desktop app bundles `anima-agent` as a Tauri sidecar for its own OS (MET-019
  "this computer"). For other devices the Device page shows a command that downloads the binary from the
  release channel the desktop updater already uses, checks its SHA-256, and runs `anima-agent enrol <code>`.
  No hub route serves binaries (K7 unchanged for that). The release build of `anima-agent` (Linux x86_64 and
  aarch64, macOS aarch64) is a deploy/release handoff. Needs a ruling.
- **D-6 Apple GPU memory number.** §6.6 says the agent shows "the GPU's share of memory in use as a number".
  K1 has no kind for it (`VRAM_*` would break MET-007). Proposal: defer the number to issue #1 as a should, and
  ship GPU use only; or a CR adds `MetricKind.GPU_MEMORY_BYTES @pending`. Needs a ruling.
- **D-7 `updateDevice` cannot set `AGENT`.** Only enrolment sets `agent`; `updateDevice(metricsSource: AGENT)`
  is VALIDATION. Revocation leaves the source as `agent` (the device shows Stale) until the operator picks
  `ssh` or `none` (MET-011). Devices handoff.
- **D-8 macOS verification.** This machine is Linux; `cfg(target_os = "macos")` code is not built by the gates.
  T4 and T5 keep macOS code thin over pure, Linux-tested functions. A `cargo check --target aarch64-apple-darwin`
  needs `rustup target add` (a toolchain download): needs the operator's yes. The live macOS proof is WP-53
  acceptance on the Mac.

## Notes for T3a and T3b (from T2 review)

- `metrics.series` is unique on `(device_id, kind, label)` with no GPU index: two GPUs of one kind would share a
  row. T3b's migration (0710–0729) must put the GPU into the key, and `series_kind_check` and
  `store/rows.rs` must accept `gpu_memory_bytes` together with the K1 member (R-091), or one stored row makes
  the device's `readings()` and `series()` `Unreadable`.
- Bridge `wire::GpuVendor` to the hub `GpuVendor` (and note WP-51's `readings::gpu` vendor type).
- R-098 (programme, 2026-11-08) rules T3b: (a) any accepted batch resets the stale timer, even with only unknown
  series; a refused batch does not; (b) `gpus` absent means unchanged, present replaces the set, `[]` means no
  GPUs now, removed GPUs' series keep history; (c) (a) and (b) go into K8 in the T3b commit that implements them;
  (d) replaced by R-099; (e) prove the
  per-device series bound (`MAX_LABELS` x kinds x GPUs in the last `gpus` list) with a test and send a cap to
  issue #1, or add a cap and refuse past it; (f) T3b owns the `wire::GpuVendor` bridge.
- R-099 replaces R-098 (d): the `metrics.series` unique key does not change. A GPU-kind series stores label =
  the GPU index as decimal text and `gpu_index` = the same index; `gpu_index` is null for every other kind.
  Ingest derives the label from the index and refuses an agent-chosen label on a GPU kind as VALIDATION
  (MALFORMED on the wire). The T3b migration adds a check (gpu_index set exactly for GPU kinds, label =
  gpu_index::text when set); in the same change the kind check accepts `gpu_memory_bytes` and K1
  `GPU_MEMORY_BYTES` loses `@pending`.
- WP-51 T3 (programme note): `SeriesKey::of` passes None for the GPU index, so a GPU-kind sample gets no key.
  Once `Sample::gpu_index` lands, T3b makes it `SeriesKey::new(sample.kind, label, sample.gpu_index)` with a test.
  T3b ingest holds pushed GPU temperature (<= 1000) and power (<= 10 000 W) to WP-51's ceilings. A finite huge value
  overflowed the running mean. store/chart.rs `SUM(a.avg * a.count)` is WP-51 T4's to fix unless T3b touches it.
