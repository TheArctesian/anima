# WP-15 Client Settings page (package plan)

Package orchestrator plan. Branch `claude/wp-15-settings`, from `phase-1` `cd91aae` (WP-16 merged), worked in the reused WP-11/WP-16 worktree (R-027). Task branches are `wp/15-settings/<task>`.

Spec: SET-001–002, UPD-006 (the slot only), CLI-002, CLI-003, API-003, NET-005, OD-2, Sections 5.5, 12 and 13.

Handoffs that apply:

- WP-11: H-3 (`useHub()` with a `<domain>Api(hub)` client), H-5 (an unreadable token is a typed `UNAUTHENTICATED`; the "sign in needed" surface belongs with sign-in) and H-7 (reserve heading height).
- WP-16: H-1 (`writeAccessToken(hub.address, …)`, `clearAccessToken(hub.address)`, `storeHubAddress`; an address change takes effect on reload; a provider uses its `address` argument).
- R-043: WP-15 builds no store of its own.

## Decisions

- **D-1 Settings page content (SET-001, SET-002).** In Phase 1, `routes/settings/+page.svelte` shows only the page title "Settings". In the desktop app it also has a place for the "Updates" row. WP-04 stage B fills that place (R-006: "the Updates row in WP-15's Settings page"), so WP-15 adds no Updates code. The nav bar already links to Settings (WP-11, NAV-001). WP-15 adds a test that the link reaches the page, which is SET-001.
- **D-2 Heading height (WP-11 H-7, R-042).** The title uses the type tokens and reserves its line height, so it does not move when the font loads.
- **D-3 Sign-in (proposal P-1, waiting for a ruling).** The plan row for WP-15 lists only the Settings page. SET-002 allows nothing else on it in Phase 1, and the spec puts the hub address field in "a later version" of Settings. But the hub refuses every operation without a token (API-003), and WP-11 H-5 and WP-16 H-1 give sign-in to WP-15. P-1 below proposes where sign-in lives. T2 waits for the ruling.

## Proposal P-1 (to the programme)

- **Sign-in route.** Add a sign-in route `apps/client/src/routes/sign-in/` and a domain folder `apps/client/src/lib/session/` to WP-15's paths.
  - `lib/session/api.ts`: `sessionApi(hub)` with `login({ username, password, totpCode })` and `logout`, following WP-11 H-3.
  - `lib/session/sign-in.ts`: the pure form rules and the outcome mapping.
  - The route renders the form: user name, password (hidden, as DEV-011), and a six-digit TOTP code (OD-2).
- **Writing the token.** When the login works, the page calls `writeAccessToken(hub.address, token)` and goes to `/devices`. When it fails, the page shows the hub's `FieldError`s or a fixed message. No token or password goes into a log (LOG-007).
- **Hub address field (CLI-002, NET-005).** The sign-in page also has the hub address field, shown with the current address. "The operator can also type the hub address" (NET-005) must happen before sign-in, so this is the only place it can go in Phase 1. Saving calls `storeHubAddress` and reloads (WP-16 H-1).
- **"Sign in needed" (H-5).** The client goes to `/sign-in` in two cases:
  - at start, when the root layout finds no stored token;
  - when any request answers `UNAUTHENTICATED`.

  `lib/session` exports one function for this. The layout calls it in one added line, in WP-11's root layout. This is the same kind of mount-line exception as R-006.
- **Sign-out (needs an operator ruling).** SET-002 allows only the title and Updates on Settings. Two options:
  - (a) Amend SET-002 to add a "Signed in as `<name>`" row with "Sign out" to the Phase 1 Settings page.
  - (b) Put "Sign out" on the sign-in page only, which would make sign-out hard to find.

  WP-15 recommends (a). Sign-out calls `logout`, then `clearAccessToken(hub.address)`, then goes to `/sign-in`.
- **Builder and reviewers.** Builder Sonnet, because sign-in has security weight. Reviewers: Sonnet, plus reviewer-security (Opus) for the token write and clear (implementation plan: login and tokens are tagged security).
