# WP-36 — Builds

Package branch: `wp-36-builds` from `main` at 8b231e0c. Each task is built on its own branch from
`wp-36-builds` and merged into it when accepted (R-067). The merge to `main` needs the operator's yes.

Requirement: R-107 (operator: "Move desktop releases off GitHub Actions and into Anima itself"). Spec: Section
3.10 (BLD-001 to BLD-082), Section 3.9 (UPD-001 to UPD-012), DNS-007, LOG-005, LOG-007, REPO-003, Sections 12
and 13. Contracts: K1 gains the builds schema part, K2 gains the `builds` tables, K3 gains the `builds` domain
(R-107).

## Constraints

- Never read `.env*`, Docker secrets, key files or `~/.config/anima/`. Never print or commit a private key.
- No push, no merge to `main`, no hub redeploy, no Cloudflare change without the operator's yes (VPS-005, DNS-008).
- Gates: `env -u DATABASE_URL BASE_REF=main bun run gates` before each review and each merge.

## Decisions

- **D-1 Builder tokens are access tokens.** `access` issues them with a new scope `builder` in
  `access.api_tokens` (on `phase-3`, also the token kind `builder`: migration 0030, R-107). The operator guard refuses that scope; a builder guard accepts only it. `builds` keeps the
  builder record (name, platform, VPN address, token id) and checks the VPN address (BLD-022, BLD-024).
- **D-2 Lease expiry is lazy and scheduled.** A claim first returns expired leases to `queued` in the same
  transaction; an upkeep job (R-072, `upkeep.rs`) also does it every 30 seconds so the Builds view is true.
- **D-3 Claims use `FOR UPDATE SKIP LOCKED`** on the oldest queued job of a matching target (BLD-004).
- **D-4 Logs** are rows in `builds.log_lines` (job, sequence, text). The store trims each job to its last 2 MB.
- **D-5 Publishing (presign, verify, copy, feed write) is task 3.** Task 1 accepts the `uploaded` report and
  stores the proposed feed; the state stays `uploading` until task 3 adds the publisher.
- **D-6 `nextReleaseVersion`** proposes the patch after the highest version that is published or under way
  (queued to uploading) on any target.
- **D-7 A failed or cancelled version may be released again.** Only a published or running version blocks
  a release of the same number (BLD-002).
- **D-8 Key blocks across reports.** `builds.jobs.log_key_lines_left` (migration 0961; 0901 before R-107) carries an open private
  key block from one report to the next, at most 200 lines. The block ends at its closing line or at the first
  line that is not key material, and a claim clears it (BLD-048, BLD-049).
- **D-9 Log lines are read three ways** (shown, spaced, strict) before they are stored. The whole line becomes
  `[redacted]` only when a stricter reading masks a value the shown one kept (BLD-049, LOG-007).
- **D-10 Until task 3, a finished build reports `FAILED`** with the fixed reason "Built and signed. Publishing
  arrives in WP-36 task 3, so this job stops here." Task 3 removes it (`TODO(WP-36 T3)`).
- **D-11 Minisign signing is written in-house** on ed25519-dalek, blake2 and scrypt. The `minisign` crate prints
  keys in `Debug`, does not zeroize and prompts. Every signature is checked with `minisign-verify`, the
  updater's own verifier, and the reference `minisign` checks it in tests (BLD-045, BLD-046).
  *Since R-116* the code is the crate `crates/updater-signature`, used by the hub; see D-36.
- **D-12 (superseded by R-116: the builder holds no key)** **The shell opens the key file dialog itself**, so the web view never names a key path. The file is
  capped at 4 KiB, and the scrypt cost at N ≤ 2^20 and p = 1. The caps stay in the crate (D-36).
- **D-13 (superseded by R-116: the hub signs)** **Signing takes only the target and version.** The shell finds the file; see D-22.
- **D-14 Job fields are strict:** the version is `MAJOR.MINOR.PATCH`, the commit is 40 lower-case hex
  characters, and the target is an enum. All are checked in Rust before any process starts.
- **D-15 Git is hardened:** hooks, fsmonitor, the credential helper, submodule recursion and system or global
  config are off, and `clean -ffdx` keeps `/target/`. Each step checks again that HEAD is the job commit and
  the tree is clean.
- **D-16 The builder token has its own key store service.** The builder id is not secret and is kept in
  `localStorage` per hub origin, so turning the builder off can revoke it.
- **D-17 The builder calls the hub through `createRequestHub`,** with requests only, no socket, and a 4 s
  limit per call, so a report goes out within 14 s (BLD-005).
- **D-18 Cancelling kills the step's process group.** The loop starts no step while it is stopping, and
  quitting the app cancels the running step.
- **D-19 (superseded by R-116 for the updater key; the builder holds none, and the `prctl` dumpable
  guard, the `ptrace_scope` warning and the locked-key BLD-028 state are removed. The note on the builder
  and operator tokens in Secret Service stands.)** **The updater key is stored sealed**, in minisign's scrypt form, never as the bare seed. Its public
  line is stored apart. The operator unlocks it once per app session, and it is then held only in shell
  memory as `Zeroizing`. Locking it, stopping the builder or quitting the app drops it. A locked key is a
  BLD-028 state, and the loop claims no job while the key is locked. A `ptrace_scope` of 0 shows a warning.
  Accepted for now: the builder token and the operator token can still be read over Secret Service by any
  process of the same user. A step sandbox (bubblewrap without the session bus) is a follow-up (issue #1).
  *Amended after the T2 security re-review:* on Linux the shell calls `prctl(PR_SET_DUMPABLE, 0)` at
  startup, so a step that crashes it gets no core dump holding the seed. The memory is guarded only when
  the process is not dumpable and `ptrace_scope` is 1 or more; otherwise the Builds row warns. An imported
  key sealed with scrypt N below 2^15 is sealed again, with a fresh salt, at N = 2^15. The operator's new
  password is used, or the same one once it has opened the file. A new password needs at least 12
  characters. On unlock, the opened key's public line must equal the stored public line, or the unlock
  fails with a fixed error (`mismatch`). The builder-token commands refuse any web view but the main one,
  as the builder and updater-key commands do (C-5).
- **D-20 On Linux the shell is a child subreaper.** After each step and on cancel, it kills and reaps every
  process the step marked, including `setsid` daemons such as `pg_ctl`. On macOS only `killpg` applies.
  *Amended after the T2 security re-review:* only processes that still carry the step marker are reaped. A
  hostile step can escape by starting a process without the marker (`setsid env -u ANIMA_BUILD_STEP
  ...`). The step sandbox (the issue #1 follow-up) closes that. The kill opens a pidfd before it reads the
  marker and signals through that pidfd, so a reused process ID is never hit. Processes the app did not
  start through a step are never killed, and the sweep waits only for marked processes and the step's
  group.
- **D-21 The repository is a seam with a transport allow-list.** It fetches `main` by full URL, with
  `GIT_NO_REPLACE_OBJECTS=1` and no graft file. A clone with foreign local config, grafts or a shallow file is
  cloned again (BLD-040, BLD-041).
  *Amended after the T2 security re-review:* a step could overwrite a loose object, forging a `main`
  commit with a new parent so that the ancestry check passed for a commit that is not on `main`. Now,
  before the ancestry check, `git fsck --no-dangling --no-progress` runs with the same fixed flags. On any
  error the clone is deleted and cloned again; a fresh clone that still fails is refused. A clone is also
  cloned again when `.git` holds `commondir`, `objects/info/alternates`, `objects/info/http-alternates`
  or `objects/info/commit-graph(s)`. git runs with `gc.auto=0` and `maintenance.auto=false`, so it never
  writes a commit graph itself. `GIT_GRAFT_FILE` points under `/dev/null`, a path no step can create, so
  git prints no deprecation hint.
- **D-22 (superseded by R-116 for signing; the bundle record still binds `SHA256SUMS` and the
  uploaded files to the bundle, D-28)** **Only the bundle record can be signed.** The record holds the commit, version, target, path and
  digest. The shell opens the file with `O_NOFOLLOW` and requires one link. It hashes and signs from that
  same descriptor, and checkout clears the record (BLD-045).
- **D-24 The hub signs for R2 itself (R-108).** SigV4 is written in the hub (`publishing/sigv4.rs`),
  tested against the AWS worked examples, with region `auto`, path-style URLs and `UNSIGNED-PAYLOAD`. A
  presigned `PUT` lives 15 minutes (D-28), names one object under `<target>/<version>/` and signs
  `host`, `content-length`, `cache-control` and `content-type`, so a builder cannot write another key,
  a longer body, other cache headers or another content type. Only the target's release files are
  granted: the updater file, the DMG on macOS and `SHA256SUMS`, each with a fixed content type. The R2
  token is read once from its two files and held as `Zeroizing`; `Bucket` and `UploadUrl` have no
  `Debug`.
- **D-25 Once the files are in, the hub owns the job.** `reportBuildUploaded` ends the lease and sets
  `publishing_since`; the job stays `uploading` and the builder's calls on it are refused. The
  publisher takes a job for 10 minutes (`publish_held_until`), runs at most 7 minutes (a `const`
  assertion keeps 3 minutes between the two) and counts its tries in `publish_attempts`, which is
  also the fence: a try that was taken over cannot end the job. The try reads the database again
  just before the stable-name copy and before each `latest.json` write, and stops when a later try
  took the job or less of its hold is left than one write may take (2 minutes), so a taken-over try
  writes no feed. Each take, hold, signed request and end reads the clock again. A hub that stops mid-publish
  takes the job again after the hold; every write is idempotent and `latest.json` is written last.
  When the answer to a `latest.json` write is lost, the hub reads the object back and the job is
  `published` if it holds the feed. An unreachable bucket three times, or three tries without an end,
  fails the job, and `latest.json` is left as it was. A job that fails while the hub publishes it
  loses its granted objects, unless a `published` job of the same target and version exists, or a
  feed write was sent for it. **Amended in T3 round 2:** the hub records `feed_sent_at` (migration
  0964) before the first `latest.json` write; from then on it never deletes the job's objects, since
  the feed may name them. A later try only confirms a sent feed: it reads each feed folder's
  `latest.json` and ends `published` when it holds the job's feed, or `failed`, objects kept, when it
  holds another. Tries that run out while the feed is unknown end `failed` with "Feed state unknown,
  check latest.json." and keep the objects. The
  operator cannot cancel a job the hub publishes: `cancelBuildJob` refuses any job that is not
  `queued`. A hub with no release bucket fails every job handed to its publisher with a fixed reason,
  so none waits for ever.
- **D-26 The upload URLs are the grant.** `buildUploadUrls` records the files it signs for in
  `builds.job_files`; the `uploaded` report must name exactly those files, sizes and digests.
- **D-27 A feed never goes back.** The floor is the highest version the target has published; a job
  below it fails (BLD-069). The same version may be published again.
- **D-28 The hub checks bytes no builder can change any more (R-108 point 8).** `buildUploadUrls`
  keeps the latest expiry of the job's URLs (`upload_urls_expire_at`, migration 0963); the publisher
  takes the job only 2 minutes after it, for clock skew. It reads each file from the R2 origin with a
  signed S3 `GET` and keeps the `ETag`; the public address only has to answer 200, because a cache
  may hold older bytes. `CopyObject` sends `x-amz-copy-source-if-match`, and 412 fails the job. The
  hub's updater key is `ANIMA_UPDATER_PUBLIC_KEY`; it must equal `plugins.updater.pubkey`, and without
  it nothing is published. After the feed, the hub reads the `ETag`s of the checked updater file and
  `SHA256SUMS` again with a signed `HEAD` and records a warning event when one changed: a builder's
  URL can outlive the check only when the hub's clock runs more than 2 minutes ahead of R2's. The builder writes `SHA256SUMS` in the shell from the bundle record, sends
  only to a URL whose path is `/<target>/<version>/<name>` of its job, uses `http` only to loopback in
  a test or debug build, and names an app built with the placeholder updater public key as a missing
  tool, so it claims no job.

- **D-29 One feed URL, no new permission (UPD-001, BLD-067, DNS-007).** `plugins.updater.endpoints` is
  `["https://releases.anima.ing/{{target}}-{{arch}}/latest.json"]`; the pubkey is the operator's public key
  (key ID 5943DAEA7084E677, replacing the placeholder), and `allowDowngrades` and `requireSignedVersion` stay `true`. The
  `main` window's `updater:allow-check`, `updater:allow-download-and-install` and `process:allow-restart`
  already cover the new URL, so `capabilities/desktop.json` is unchanged.
- **D-30 A failed update says why (UPD-002, UPD-006, BLD-068).** `desktopUpdater` sorts the plugin's error
  text into `no-feed` (404, no release JSON, no entry for the target), `signature` (bad signature, other
  key, other or missing signed version) or `other`, and keeps only that word on `UpdaterError.reason`, never
  the text (LOG-007). The schedule's `failed` state carries it and logs one fixed line for each
  (`NO_FEED_LINE`, `SIGNATURE_REFUSED_LINE`, else the old two). The Settings row says so in words; on a Mac
  a missing feed reads "Updates for the Mac are not published yet" because BLD-068 makes that normal.
- **D-31 The proof runs the real plugin (UPD-002, BLD-067 to BLD-069).** `apps/desktop/src-tauri/tests/updater/`
  uses `tauri` `test` (mock runtime) and `tauri-plugin-updater` with the shipped `plugins.updater` block,
  a loopback server and a minisign key pair made in memory per test (never written, never the operator's).
  The shipped endpoint's origin is swapped for the loopback one, so the plugin's own `{{target}}-{{arch}}`
  substitution is what the server sees. It replaces the planned `deploy/release/local-proof.ts`, because
  the plugin's version and signature code cannot be reached from TypeScript. The manual two-AppImage steps
  are in `docs/releases.md`.
- **D-32 `requireSignedVersion` is proved by an unversioned signature.** The plugin refuses a signature
  that names another version whatever the setting; the setting only decides about a signature that names
  none (`MissingSignedVersion`). The mutant `requireSignedVersion: false` survived the first mismatched-
  version test and is killed by `upd_002_a_signature_that_names_no_version_is_refused`.
- **D-33 The workflow is gone; the DNS record stays (R-114, DNS-007).** R-114 removed
  `.github/workflows/release.yml`, `deploy/release/` and their tests, so T4 takes phase-3's removal and
  `docs/releases.md` of phase-3 as its base. The `updates.anima.ing` record, its tests and its README and
  `vpn.md` rows stay in the repo's DNS definition until the operator says yes to the Cloudflare change
  (DNS-007). The app reads `releases.anima.ing` only.
- **D-34 The hub signs; the key is a Docker secret (R-116, BLD-045, SEC-004).** `ANIMA_UPDATER_KEY_FILE`
  (`/run/secrets/updater_key`, the `tauri signer generate` file) and `ANIMA_UPDATER_KEY_PASSWORD_FILE`
  (`/run/secrets/updater_key_password`, empty for no password) are read once at start, each with a cap
  (4 KiB and 1 KiB) into `Zeroizing` memory; one trailing newline is dropped. `UpdaterKey` and its
  `SecretKey` have no `Debug`, `Display` or `Clone`, and `UpdaterKeyError` has fixed texts that hold
  only an `io::ErrorKind` or a fixed signature error. A key that does not open, a public key that is
  not `ANIMA_UPDATER_PUBLIC_KEY`, or no public key turns publishing off: the hub logs one fixed
  warning, starts without a bucket and fails each job it is given with the fixed `PUBLISHING_OFF`
  reason. The R2 token alone never publishes.
  *Amended by D-44 and CR-26:* the two files live in the folder `secrets/updater/`, mounted at
  `/run/secrets/updater/`, which are the defaults now; an absent file also turns publishing off.
  The password may be empty only for an unencrypted key.
- **D-35 Signing is deterministic, so a retry is idempotent (BLD-046, D-25).** The trusted comment is
  `timestamp:<uploading_at>\tfile:<name>\tversion:<version>`, with the job's `uploading` time (or its
  creation time), and ed25519 is deterministic. Every try of a job writes the same `.sig` bytes, so a
  `.sig` whose answer was lost, or that a stop cut short, is put again whole by the next try.
- **D-36 The signature covers exactly the verified bytes (BLD-046, BLD-064).** The first signed `GET`
  that checks size, SHA-256 and `ETag` also feeds the minisign prehash; the hub signs that digest. Before
  anything public is written, a second signed `GET` pinned to the same `ETag`, size and SHA-256 streams
  the file through `SignatureStream`, which must verify for the job version with
  `ANIMA_UPDATER_PUBLIC_KEY`. A file that changes between the reads fails the job.
- **D-37 Order of writes (BLD-066, D-25).** `<file>.sig` (`Cache-Control: public, max-age=3600`,
  `text/plain`) is written first, then the stable copy, then `latest.json` last. A fence
  (`tried.holds()`) precedes each write. The feed's `signature` is the `.sig` text.
- **D-38 A builder's feed carries no signature (BLD-063, BLD-065).** Each proposed entry must be
  exactly `{"url"}`; a feed with a `signature` is refused, so the hub never trusts a builder's text.
- **D-39 Confirming a sent feed reads the bucket `.sig` (D-25).** When a try finds `feed_sent_at` set,
  it reads `<file>.sig` (at most 4 KiB), checks it parses with the configured key, rebuilds the signed
  feed and compares it with the `latest.json` in the bucket.
- **D-40 A failed job deletes its `.sig` too (BLD-070).** The delete is sent whether or not a `.sig` was
  written; deleting a missing object is a no-op in R2.
- **D-41 The builder signs nothing (R-116, BLD-044, BLD-028).** Removed from the shell and client: key
  import, unlock and lock, the updater key store entry, the sign step, `KeyReadiness`, the locked
  BLD-028 state, the `prctl(PR_SET_DUMPABLE)` guard and `ptrace_scope` warning, and the Settings →
  Builds key rows. *Amended after the T6 security review (S-1):* removing the code did not remove the
  key: the entries the T2 import wrote, `ing.anima.desktop` / `updater-key` (the sealed key) and
  `updater-key-public`, stayed in each builder's key store. The shell now deletes both at every
  start, off the main thread; a missing entry is not an error, and a failure logs only its code.
  `docs/releases.md` gives the operator the manual commands too. The builder uploads the unsigned
  updater file and `SHA256SUMS` and gets no `.sig` URL. The log redaction of key-shaped text and of `TAURI_SIGNING_PRIVATE_KEY` stays (BLD-049).
- **D-42 `isMac` excludes iOS (UPD-006).** `isMac(userAgent)` in `$lib/platform` is true for
  `Macintosh` or `Mac OS X` and false when the agent also names iPhone, iPod or iPad, so the Updates
  row says "Updates for the Mac are not published yet" only on a Mac.
- **D-43 A builder call never drops a transaction that holds a lock (BLD-004, BLD-029, D-25).** The
  claim, report, uploaded report, lease expiry and upload URL paths run their work in a function on
  the caller's connection, and `jobs::ended` commits the transaction on success and rolls it back on
  any error, as `publishing/tries.rs` does since 0e999205. A dropped sqlx transaction rolls back only
  later, from a task, so a refusal after `FOR UPDATE` left the job locked and the next claim or
  publisher take (`SKIP LOCKED`) passed it by. Tests: `FOR UPDATE NOWAIT` from another thread after
  a refused report, uploaded report and upload URL request. A claim refuses only before it locks
  (an unenrolled builder has no row), so its other error paths are database errors and have no test.
- **D-44 An absent updater key file never stops the hub (R-116, CR-26, SEC-004).** Docker Compose
  5.7 with Engine 29.9 refuses to create a container whose `secrets: x: file:` is absent:
  `docker compose config` and `up --dry-run` only warn ("secret file … does not exist"), but `up`
  fails with "invalid mount config for type "bind": bind source path does not exist". An empty
  file is mounted. So the pair is not a compose secret: compose mounts the folder
  `./secrets/updater` read-only at `/run/secrets/updater` (SELinux `z`, like the other binds), and
  creates it empty when it is absent. `ANIMA_UPDATER_KEY_FILE` and
  `ANIMA_UPDATER_KEY_PASSWORD_FILE` default to the two files in it, and compose sets them too. A
  missing file turns publishing off (D-34). `bin/preflight` warns and passes when either file is
  absent; a file that is there must have mode `0440`, and the key must not be empty. The R2 token
  files stay compose secrets, so the same rule does not hold for them: while one is absent, compose
  does not start the hub and preflight fails. They are in place on the VPS (operator changes,
  2026-11-12); moving them into a folder would change the VPS and is left to the operator.
